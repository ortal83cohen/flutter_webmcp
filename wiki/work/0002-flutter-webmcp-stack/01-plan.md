# Plan: Flutter WebMCP package skeleton

## Goal

After this change the repository contains a working, self-checking Flutter package skeleton: a named Dart package rooted at the repository root, a runnable Flutter web example that registers tools against the package's registry, a test suite that has been demonstrated to report failure, a committed formatter and analyzer configuration, one documented command that runs the whole check suite end to end, and a CI workflow that runs that same command alongside the existing wiki lint. An engineer cloning the repository can run one command and see every stage pass, and can run the example in Chrome and see the registered tool names and the active transport identifier on screen. The browser's WebMCP API is not called anywhere; the skeleton stops at a detection-and-log seam.

## Approach

The package is rooted at the repository root, not in a subfolder. `pubspec.yaml`, `analysis_options.yaml`, `lib/`, `test/` and `example/` sit beside the existing `wiki/`, `tools/` and agent configuration. The package name is `webmcp_pilot`, with `webmcp_autopilot` as the pre-decided fallback if the first is taken; step 1 settles this before any file names the package. Rooting the package at the repository root is what makes the root `README.md` the package's pub.dev README, which is why the README edit in step 10 inserts the package section *above* the existing scaffold content rather than appending below it.

The Dart side is a plain singleton registry with no widget-tree dependency, per the research artifact's registry finding. A single public library file, `lib/webmcp_pilot.dart`, exports the whole public surface; everything else lives under `lib/src/` and is never imported directly by a consumer or by the package's own public-surface test. The registry holds a name-keyed map of tool descriptors, validates tool names against the spec's character rule, rejects duplicates, dispatches invocations to the registered handler, and notifies a transport on every registration change. A second, deliberately minimal extension point, a tool-source interface, exists so the later `go_router` adapter is additive rather than a change to the registry: a source returns a list of tools and the registry registers them through the same validating path.

Platform isolation is a conditional export, named explicitly here so no step has to guess. The file `lib/src/transport/transport_selector.dart` exports the non-web implementation by default and the web implementation when the compile-time constant `dart.library.js_interop` is available. Both implementation files declare the same top-level factory function, and every other file in the package imports only the selector. The web implementation performs feature detection with the presence check from `dart:js_interop_unsafe` and writes one log line per event; it never reads the `modelContext` getter and never calls a browser method. The getter itself is declared once, in `lib/src/interop/document_model_context.dart`, as an extension adding an external member to `package:web`'s `Document` type, so that when `package:web` eventually ships the real binding the workaround is a one-file deletion.

The analyzer binary for this repository is **`dart analyze`**, invoked exactly once from the repository root by the check script and by CI. This is a deliberate, single decision that every step, the check script and every acceptance criterion is written against; the reasoning and its cost are in the next section. The check script is `tools/check.sh`, a POSIX shell script with a preflight and six numbered stages — wiki lint, dependency resolution, format check, static analysis, tests, web build — in that fixed order, aborting at the first failing stage and naming it. `AGENTS.md` gains a `## Checks` section naming that script as the full-suite command, so every later pipeline phase runs what CI runs.

## Why this approach

**`dart analyze` over `flutter analyze`.** `flutter analyze` rewrites a committed `analysis_options.yaml` in place the first time it runs in a workspace: it prints an upgrade notice and injects an `analyzer` exclude block covering build and platform directories into the tracked file. That was reproduced twice against this repository's toolchain during the previous validation rounds. A check command that mutates a reviewed configuration file makes every CI run start from a dirty working tree and makes the effective analysis scope depend on a block nobody reviewed. `dart analyze` does not do this. The cost of the choice, accepted knowingly: `dart analyze` is the less familiar command for Flutter developers, and it does not resolve dependencies for you, so the check script must run the dependency stage before the analysis stage — which it does, and which is why the stage order in the script is fixed rather than advisory. A single invocation from the repository root reaches the nested `example/` package, creating a separate analysis context from `example/pubspec.yaml` and applying `example/analysis_options.yaml`'s own relaxed rule set within that same invocation, so exactly one invocation is planned and a second would be redundant.

**Explicit exclusions over tool defaults.** The analysis stage's scope is stated in the Interfaces section as a fixed list of what is and is not analyzed, and the exclusions that produce it are committed in the two options files rather than inherited from any binary's default or self-injected block. `example/build/` exists by the time checks run in a warm tree — the build stage created it on an earlier run — and the analyzer walks it unless told otherwise.

**Singleton registry over a widget-based one.** Taken from the research artifact's registry finding: a widget-based registry cannot be unit-tested without pumping a tree, gains nothing for router introspection, and carries a `BuildContext` dependency that a future non-Flutter consumer would have to strip. The optional widget wrapper remains additive and is out of scope here.

**Detection-only web transport over a real browser call.** WebMCP is a Community Group draft in a Chrome-only origin trial whose lifecycle details have already changed release over release. Calling it from the skeleton would put an unstable, un-unit-testable dependency in the critical path of the first check suite. The seam costs one interface and two implementations; the call itself is a later work item.

**No committed lock files over a lock file plus a version-pin file.** A published library package resolves against ranges, and the example is not a deployed application, so nothing is gained by committing either lock file — and without a committed lock file there is no artifact for CI's installed Flutter version to drift from. The Flutter version is therefore pinned in exactly one place, a single literal in the CI workflow's package job, and the job prints the resolved version so the pin is observable in the log. This replaces the `.fvmrc`-style pin considered earlier, which would have introduced a second file whose format and reader both had to be specified to be worth anything.

**Unresolved research items, and why none blocks this plan.** The research artifact leaves eight items open. The Chrome testing-flag question and the `outputSchema` mechanism are moot because no browser call is made here. Per-screen tool shadowing is *decided* by this plan rather than left open: the skeleton has one flat tool namespace and no shadowing. The capability diff against the competing packages and the third prior-art package are prerequisites for the publishing work item, and publishing is out of scope. Whether `dart-lang/web` plans to ship `modelContext` is handled structurally by confining the extension to one file. The pana rule text on deprecated interop libraries is moot because the hygiene test forbids those imports outright regardless of how pana scores them. The maintenance status of the reference JavaScript toolkit affects no file here. No open item blocks a decision this plan makes.

7. **Create the example package.** Touches `example/` in full: generate a web-only Flutter application scaffold named `webmcp_pilot_example` into that directory, then trim it to `example/pubspec.yaml`, `example/analysis_options.yaml`, `example/web/`, `example/lib/main.dart`, `example/lib/example_tools.dart` and `example/test/example_tools_test.dart`. The manifest declares `publish_to` as none and depends on the root package by relative path. The tool-registration logic lives in `example_tools.dart` so it is testable without a widget tree; `main.dart` shows the counter, the registered tool names and the transport identifier. Complete when dependency resolution, `flutter test` inside `example/` and `flutter build web` inside `example/` each exit zero and `example/build/web/index.html` exists.

8. **Write the check script.** Touches `tools/check.sh`, executable, strict-mode shell, resolving the repository root from its own location so it runs from any directory. Preflight plus the six stages in the fixed order from the Interfaces section, each printing one line naming the stage and its outcome, aborting at the first failure with a non-zero exit status. Complete when the script exits zero on the clean tree and prints the preflight line plus six stage lines.

9. **Prove the suite reports failure.** Touches no committed file. Invert one assertion in `test/registry_test.dart`, run the check script, capture the failing output and the non-zero exit status, revert, run again and capture the passing output. Complete when both outputs are pasted into the verification artifact and `git status --porcelain` is empty afterwards.

10. **Write the documentation set.** Touches `README.md` (edited), `CHANGELOG.md` and `LICENSE` (new), and `AGENTS.md` (edited). The README edit inserts one new top-level section — a level-one heading naming the package, a short description, an installation paragraph, a usage paragraph and a status paragraph naming the origin-trial constraint — immediately above the file's current first line, leaving every existing line byte-identical below it and producing a file with two sequential level-one headings. No existing heading is touched or renumbered, and the sentence naming the Cursor third-party-plugins toggle stays exactly as it is because an ADR depends on it. `AGENTS.md` gains a `## Checks` section naming the four commands from the Interfaces section. Complete when the README diff shows insertions only above the previously-first line, and `python3 tools/lint_wiki.py` exits zero.

11. **Add the CI job.** Touches `.github/workflows/checks.yml`. Add a second job named `package` beside the existing `wiki` job, leaving every existing line of the `wiki` job unchanged. ## Interfaces and shared decisions

**Package identity.** Name `webmcp_pilot` (fallback `webmcp_autopilot`), version `0.1.0`, description one sentence between sixty and one hundred eighty characters naming WebMCP and Flutter web. The `repository` field is the canonical HTTPS URL of this repository's `origin` remote, read from the git configuration rather than typed from memory. The `environment` Dart constraint's lower bound is the Dart version bundled with the pinned Flutter release, and never below 3.4 because `package:web` requires it. Dependencies: the Flutter SDK, and `package:web` at a caret range whose lower bound is 1.1.1. Development dependencies: `flutter_test` from the SDK and `flutter_lints` at a caret range. A `platforms` map declares web and nothing else. The example manifest declares name `webmcp_pilot_example`, `publish_to` set to none — omitting it makes a path-dependency example produce an invalid-dependency analyzer warning that fails a fatal-infos run — a relative path dependency on the root package, the Flutter SDK, `flutter_test` and `flutter_lints`, and no `platforms` map.

**Public surface.** `lib/webmcp_pilot.dart` exports: the `WebMcp` class, the `WebMcpTool` descriptor, the `WebMcpToolHandler` function type, the `WebMcpToolSource` interface, the `WebMcpTransport` interface, and the four exception types. `WebMcp` is a singleton reached through a static `instance` getter with a private constructor. Its seven public operations are: `registerTool` taking a descriptor; `registerSource` taking a source and registering every tool the source returns through the same validating path as `registerTool`; `unregisterTool` taking a name and returning a boolean, true when a tool was removed and false when no tool of that name was registered, never throwing for an absent name; `tools`, returning an unmodifiable list of descriptors sorted ascending by name; `invokeTool`, taking a name and an argument map and returning a future of a nullable object; `reset`, taking an optional transport, which clears all registrations and installs either the given transport or a freshly created default one; and `transportId`, a synchronous string getter naming the active transport.

**Data shapes.** `WebMcpTool` is an immutable class with a `name` string, a `description` string, an `inputSchema` map from string to nullable object stored as an unmodifiable copy and defaulting to empty, and a `handler`. `WebMcpToolHandler` takes an argument map from string to nullable object and returns a future-or of a nullable object. `WebMcpToolSource` declares one method returning a list of descriptors. There is no runtime configuration: no environment variables, no configuration file, no constructor parameters other than those named here.

**Error handling.** One abstract base, `WebMcpException`, implementing `Exception`, carrying a message and a tool name, whose string form begins with the concrete class name and includes the tool name. Three concrete subtypes: `WebMcpInvalidToolNameException`, thrown by registration when a name is not between one and one hundred twenty-eight characters drawn from ASCII letters, digits, underscore, hyphen and period; `WebMcpDuplicateToolException`, thrown by registration when the name is already registered, leaving the existing registration untouched; and `WebMcpToolNotFoundException`, thrown by invocation when no tool of that name is registered, without invoking any other handler. Exceptions thrown by a tool handler propagate to the caller of `invokeTool` unwrapped and unlogged.

**Transport seam.** `WebMcpTransport` declares a string `id` getter and two void notification methods, one for registration and one for unregistration. The non-web implementation is `NoopTransport` with identifier `noop` and empty methods; it logs nothing. The web implementation is `WebDetectionTransport` with identifier `web-detection`; on construction it records whether the document object has a `modelContext` property, using the presence check from `dart:js_interop_unsafe`, and writes one line per construction and per notification through `dart:developer`'s log with the logger name `webmcp_pilot`. It never reads the `modelContext` value and never calls a method on it. `lib/src/transport/transport_selector.dart` is the conditional export: the non-web file by default, the web file when `dart.library.js_interop` is available. Both files declare a top-level factory function `createDefaultTransport` returning a `WebMcpTransport`. No file outside the selector imports either implementation.

**Check stages.** `tools/check.sh` runs a preflight that fails with a message naming the missing binary if either `flutter` or `dart` is absent from the path, then six stages in this fixed order: (1) wiki lint, running `python3 tools/lint_wiki.py`; (2) dependencies, running `flutter pub get` at the root and then inside `example/`; (3) format, running the Dart formatter in check-only, exit-if-changed mode over exactly the three paths `lib`, `test` and `example/lib`, never over the repository root, so generated output is never inspected; (4) analysis, running `dart analyze` once from the repository root with infos and warnings both made fatal by explicit flags; (5) tests, running `flutter test` at the root and then inside `example/`; (6) build, running `flutter build web` inside `example/`. Each stage prints one line naming the stage number and its outcome. The script aborts at the first failing stage and exits non-zero.

**Analysis scope, stated without relying on any tool default.** Analyzed: every Dart file under `lib/`, `test/`, `example/lib/`, `example/test/` and any other tracked Dart file under the repository root. Not analyzed: everything under `example/build/`, excluded by an entry in `example/analysis_options.yaml` naming that directory relative to its own location; everything under any `.dart_tool` directory, excluded by explicit entries rather than by the analyzer's hidden-directory behaviour; and nothing else. The root `analysis_options.yaml` carries a matching exclusion naming the example build directory as a safeguard for the case where the example's own options file is ever removed; the entry that governs files under `example/` is the one in `example/analysis_options.yaml`. The root options file includes the `flutter_lints` rule set and additionally requires documentation comments on public members; the example's options file includes `flutter_lints` only, deliberately relaxed, since example code is not published API.

**Forbidden import list and secret-token list.** `test/repo_hygiene_test.dart` fails if any Dart file under `lib/` or `example/lib/` imports `dart:html`, `dart:js`, `package:js`, `dart:io` or `package:http`, and fails if any file under `lib/`, `example/lib/`, `tools/` or `.github/` contains any of the fixed literal markers for a private-key header, an AWS access-key prefix, or the words for an application key or a password used as an assignment target. Both lists are fixed here so no step invents its own.

**Documented commands.** `AGENTS.md`'s `## Checks` section names exactly four: the full suite is the check script invoked through the shell; a single test is the Flutter test runner given one file path; format is the Dart formatter over the three source paths; analyze is `dart analyze` with the fatal flags from the repository root. The CI package job runs the full-suite command verbatim, as one step.

## Rollback

Every change is either a new file or one of four edits to existing files: `README.md`, `AGENTS.md`, `.gitignore` and `.github/workflows/checks.yml`. Reverting the implementation commit restores all four to their present contents and deletes the new files. There is no database, no schema, no migration, no deployed service and no published artifact, so nothing outside the repository depends on the change.

Three things a revert does *not* undo, stated plainly. First, network side effects already performed: step 1 queries pub.dev, and every dependency-resolution and build stage contacts the package server and the SDK artifact host, downloading packages into the machine-local pub cache; the cache entries survive the revert, though they are inert. So the claim "no external service is contacted" would be false and is not made. Second, any branch pushed to the remote to observe CI — which step 11's completion condition and one acceptance criterion both require — stays in the remote's history along with its Actions run and logs until someone deletes the branch explicitly; reverting a local commit does not remove it. Third, the pub.dev name is not claimed by this work item because nothing is published, so the name remains freely changeable here; it becomes a genuine one-way door only in the later publishing work item, which is out of scope.

No step in this plan is a one-way door. Two items nonetheless need a human before they harden: the licence and its copyright holder, and the validation-round-cap conflict named in the risk table.

## Out of scope

Calling the browser's WebMCP API at all — registration, discovery, execution, the `toolchange` event and the `AbortSignal` unregistration mechanism are all deferred. The `go_router` adapter and navigation-tool generation: only the tool-source interface exists here, with no implementation. The dev-time non-browser transport: only the transport interface exists here. The optional widget wrapper for lifecycle-tied registration. Per-screen tool shadowing — this plan decides against it for the skeleton. Publishing to pub.dev, running pana, and the capability diff against the competing packages. The declarative form-annotation API, which the research artifact already rules inapplicable. Typed input decoding and output schemas. Browser-based integration or end-to-end tests. Support for any platform other than web. Community-health files beyond the licence and changelog. Any change to the existing wiki job in the CI workflow, to the existing wiki content, or to the agent configuration other than the `## Checks` section added to `AGENTS.md`.

## Verification approach

Every acceptance criterion in `02-criteria.md` is checked in one of four ways, and each criterion's negative case is a concrete mutation applied to the working tree, one at a time, reverted immediately after the observation, with `git status --porcelain` empty again before the next one is applied.

Most criteria are exit-code checks: run `tools/check.sh`, or one named stage of it, and read the exit status and the stage lines. The registry, transport, hygiene and example-tool criteria are covered by the six named test files from steps 6 and 7 and are exercised by the test stage. Three checks are not exit-code based and are named here so no one expects a command for them: the README criterion is checked by reading the diff and confirming that every insertion sits above the previously-first line and that the ADR-referenced sentence is unchanged; the CI job-independence criterion is checked by reading the workflow file and confirming that neither job definition declares a dependency key, which needs no push; and the version-pin criterion is checked by reading the workflow for a single version literal and then reading the pushed branch's job log for the printed resolved version.

Fixtures are transient and never committed: a Dart file placed under `example/build/` containing a deliberate analyzer error, used to prove the build-output exclusion is load-bearing; a fake transport class defined inside the transport test; and a counter holder defined inside the example test. The demonstration that the suite reports failure is step 9's inverted assertion, with both the failing and the passing outputs pasted into the verification artifact.
