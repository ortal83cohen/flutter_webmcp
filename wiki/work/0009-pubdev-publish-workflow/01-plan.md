# Plan: Publish webmcp_flutter to pub.dev on every push to main with a patch bump

## Goal

After this change, a push to the main branch of this repository produces, without human keystrokes, a new patch version of the webmcp_flutter package on pub.dev, and a matching commit and annotated tag on main. An observer can see three things after a successful run: the version line in pubspec.yaml has its third component incremented by one, CHANGELOG.md carries a new dated section for that version at the top, and the pub.dev versions list for webmcp_flutter contains the new version. The previously published versions 0.1.0 and 0.1.1 are never re-uploaded; the first version this automation can produce is 0.1.2. No pub.dev password, token or credentials file is stored anywhere in the repository.

## Approach

The work splits into two GitHub Actions workflow files and one shell helper, because pub.dev refuses to authenticate a publish that was not started by a git tag push. This is the single fact that shapes the whole design: the research artifact records that automated publishing from GitHub Actions is accepted only for tag-triggered runs, so a job that runs on a branch push can bump and tag but can never publish, and a job that can publish can only be started by the tag.

The first workflow file is named release.yml and lives in the .github/workflows directory. It listens to pushes on the main branch only. Its single job first checks that the repository secret named RELEASE_GITHUB_TOKEN is non-empty and fails immediately if it is not, before any checkout or any git write. It then checks out the repository using that secret as the credential, installs Python and the same pinned Flutter version the existing checks workflow uses, and runs the package check suite the repository already owns, the shell script at tools/check.sh. Only after that suite passes does the job call the new helper script to compute and write the bump, verify that no tag for the new version already exists, commit the two changed files, create an annotated tag, and push first the commit and then the tag using the secret. The default GitHub Actions token cannot be used for the push, because the research artifact records that events created with it do not start new workflow runs, which would leave the tag pushed and the publish workflow never started.

Because that push does start new runs, the bump commit lands on main and re-enters this same workflow, so the job needs a loop guard. The guard is a job-level condition owned by this repository: the job runs only when the head commit message of the push does not begin with the release prefix that this job itself writes. No GitHub skip instruction is used anywhere in this design. The research artifact records that a skip instruction is scoped to the runs the marked commit would trigger, and the annotated tag points at that very commit, so a marker in the release commit message risks suppressing the tag-triggered publish run, which is the only run able to publish. The research artifact also records that a condition comparing the triggering actor against the GitHub Actions bot cannot help here, because a push authenticated with a personal access token or an App installation token reports the token owner as the actor, never the bot; that guard is therefore not used.

The second workflow file is named publish.yml, also in the .github/workflows directory. It listens only to pushes of tags whose name is the letter v followed by three numeric, dot-separated components. Its one job calls the official reusable publish workflow published by the Dart team in the dart-lang setup-dart repository, at the v1 reference, and grants the identity-token write permission that the OpenID Connect exchange requires. This file contains no secret, because the authentication is a short-lived token signed by GitHub and exchanged with pub.dev.

The version arithmetic and the changelog edit live in a new shell helper at tools/bump_patch_version.sh rather than inside the workflow YAML, so that the logic can be tested offline against fixtures and so the workflow file stays a thin sequence of named steps. The helper reads pubspec.yaml and CHANGELOG.md from a repository root it is given, validates both, writes both, and prints only the new version string on standard output. It performs no git operation and touches no network. The git commit, the annotated tag, the push and the secret check belong to the workflow YAML alone. A companion test script at tools/test_bump_patch_version.sh exercises the helper against a set of fixture directories, and is added as a new stage at the end of tools/check.sh so that every pipeline phase and the existing continuous-integration package job run it.

## Why this approach

The research artifact lists six options. Publishing from the main-branch job with OpenID Connect was rejected because pub.dev rejects runs that no tag started, so that option cannot work at all. Tag-only publishing with humans doing the bump and the tag was rejected because the user chose a bump on every push to main. A long-lived pub credentials JSON secret was rejected because the official documentation prefers OpenID Connect and because a stored credential has to be rotated and can leak. Extending the existing checks workflow with a publish job was rejected because that workflow runs on every branch and on pull requests, so a release concern would be coupled to an all-branch check and the package suite would run twice on main. Publishing without committing the bump was rejected because git and pub.dev would then disagree about the current version and the next bump would compute a version that already exists.

Two smaller choices also had alternatives. The bump arithmetic could have been written inline in the workflow with a stream editor invocation; it is a helper script instead so that it has a test that runs without a network and without GitHub. The version could have been read with the yq tool named in the version-bump research file; the helper instead matches the top-level version line with a plain-text pattern, because yq is one more dependency to install on the runner and the pubspec version line in this repository is a single unindented key.

## Steps

1. Write the helper script at tools/bump_patch_version.sh. It accepts an optional first argument naming the repository root and defaults to the directory above its own location. It reads the top-level version key of pubspec.yaml in that root, requires exactly three numeric dot-separated components with no prerelease or build suffix, and computes the new version by adding one to the third component while leaving the first two unchanged. It reads CHANGELOG.md in that root, requires the first non-blank line to be the single-hash Changelog title, and requires that no existing section heading in the file names the computed new version. It then writes both files and prints the new version, and nothing else, to standard output. Complete when the script exists, is executable, exits zero on a valid repository root, and exits non-zero without writing either file for each rejected input named in the interfaces section.

2. Write the fixture set and the test script. Fixtures live under tools/fixtures/bump-patch-version, one directory per case, each holding a pubspec.yaml and a CHANGELOG.md. The test script at tools/test_bump_patch_version.sh copies each fixture into a temporary directory, runs the helper against the copy with a fixed release date supplied through the environment, and compares the resulting files and exit status against what the case expects. Complete when the test script exits zero, covers every positive and negative case in the criteria file, and makes no network call.

3. Add the helper test as a new final stage of tools/check.sh, following the existing stage numbering, message and failure-reporting pattern in that file. Complete when the full check suite runs the helper test and reports the new stage as passed.

4. Write the release workflow file at .github/workflows/release.yml, with the trigger, concurrency, release-prefix loop guard, secret gate, toolchain setup, check step, bump step, tag-collision guard, commit, annotated tag and push described in the interfaces section, and with a short English operator note in comments naming the two human prerequisites. Complete when the file parses as YAML, the secret gate is the first step of the job, the toolchain setup steps precede the check step, and no step runs unconditionally after a failed earlier step.

5. Write the publish workflow file at .github/workflows/publish.yml, with the tag trigger, the identity-token write permission and the call to the official Dart reusable publish workflow at v1, plus a comment naming the tag pattern the operator must configure on pub.dev. Complete when the file parses as YAML and references no repository secret.

6. Verify without releasing. Run the wiki lint and the full check suite locally, confirm both workflow files parse, and confirm that the working tree still shows version 0.1.1 in pubspec.yaml, no new changelog section and no new git tag, because implementation must not itself perform a release. Complete when the command output for each of these is recorded in the verification report.

## Interfaces and shared decisions

Workflow file names and job identifiers. The bump workflow file is .github/workflows/release.yml, its workflow name is release, its single job identifier is bump-and-tag. The publish workflow file is .github/workflows/publish.yml, its workflow name is publish, its single job identifier is publish.

Release workflow trigger. Push events on the branch main only. No pull-request trigger, no manual dispatch trigger, no tag trigger. Manual dispatch is deliberately absent because the research artifact records that pub.dev rejects a publish that a tag did not start, so a dispatchable publish path would be a trap.

Publish workflow trigger. Push events on tags matching the letter v followed by three groups of one-or-more digits separated by dots. Nothing else.

Loop guard. The bump-and-tag job carries exactly one job-level condition: the head commit message of the triggering push must not begin with the release commit prefix defined below, which is the words chore and release in the conventional form followed by a space and the letter v. This is the only loop guard, it is evaluated from the push payload by GitHub rather than suppressing the run, and it therefore cannot affect the tag-triggered publish workflow. No GitHub skip instruction appears in any commit message this automation writes, and no actor comparison is used, for the reasons recorded in the research artifact and repeated in the approach section.

Concurrency. The bump-and-tag job declares a concurrency group whose key is the literal string release-main and sets cancellation of in-progress runs to false, so that two pushes landing close together do not race on the same patch number. The queue holds one running run and one pending run: when a third push arrives while one run is executing and one is already queued, it replaces the queued one, so the middle push contributes its commits to a later release rather than to a release of its own. That is accepted, because the surviving run bumps from whatever version main then holds. Cancellation is never enabled, so the job needs no actions write permission.

Permissions. The bump-and-tag job requests read access to repository contents only, because every git write is performed with the RELEASE_GITHUB_TOKEN secret rather than the default token. The publish job requests identity-token write and contents read, as the official example does.

The secret. One repository secret, named RELEASE_GITHUB_TOKEN, holding a personal access token or GitHub App installation token with write access to repository contents. It is used as the checkout credential and therefore for both pushes. The first step of the bump-and-tag job reads that secret into an environment variable, and exits non-zero with an English message naming the secret when the value is empty. The job fails closed: it stops there, before checkout, so a missing secret can never leave a half-finished bump in git.

The helper contract. The script is tools/bump_patch_version.sh, run with a POSIX shell. Its optional first positional argument is the repository root; with no argument it uses the parent directory of the directory holding the script. It reads an environment variable named RELEASE_DATE and, when that variable is non-empty, uses its value verbatim as the changelog date; otherwise it uses the current date in Coordinated Universal Time formatted as four-digit year, hyphen, two-digit month, hyphen, two-digit day. Standard output carries exactly one line, the new version string with no v prefix and no other text; every diagnostic goes to standard error. Exit status zero means both files were written; any non-zero status means neither file was written.

Helper input validation and error handling. The helper exits non-zero, writes nothing and explains itself on standard error in each of these cases: pubspec.yaml is absent or has no top-level version key; the version value is not exactly three dot-separated runs of digits, which includes any prerelease or build suffix; CHANGELOG.md is absent or its first non-blank line is not the single-hash Changelog title; a section heading naming the computed new version already exists in CHANGELOG.md. Both new file contents are computed in memory and validated before either file is written, so a rejected input leaves the working tree untouched.

The duplicate-heading rejection is a consistency check between the two files, not an idempotency check on repeated runs. Running the helper twice in a row succeeds twice, because the first run advances the pubspec version and the second therefore computes a further version that no heading names. The case the rejection catches is a pubspec and a changelog that disagree, for instance a pubspec at 0.1.1 beside a changelog that already documents 0.1.2, which is the state a partially applied or hand-edited bump leaves behind. The test fixture for this case must set up that disagreement directly; a second consecutive run does not exercise it.

Passing the new version between steps. The helper step in the release workflow is a named step whose identifier is bump. It captures the helper's single standard-output line and appends it to the file named by the step-output environment variable under the key version. Every later step that needs the value, namely the tag-collision guard, the commit message, the tag name and the tag annotation, reads it from that step's output rather than recomputing it or re-reading pubspec.yaml, so all four always name the same version.

Toolchain setup in the release job. Before the check step, the job installs the same toolchain the existing checks workflow installs: the Python setup action at the version that workflow pins, and the Flutter setup action at the channel and pinned version that workflow names. This is required rather than cosmetic, because tools/check.sh aborts in its preflight when the flutter or dart binary is missing and invokes python3 for the wiki lint.

Changelog format. The helper inserts, immediately after the Changelog title line and separated from it by one blank line, a heading consisting of two hash characters, one space, the new version, one space, a hyphen, one space and the date. No square brackets, no Keep-a-Changelog vocabulary, because the two existing sections in this repository use the bracket-free form. Below that heading, one blank line, then exactly one bullet line, then one blank line before the previously top-most section. Existing content is never rewritten or reordered.

The bullet line is fixed here so that the helper's test cannot assert whatever the helper happens to produce. It is a hyphen, one space, then the English sentence stating that this is an automated patch release from main, capitalised as a sentence and closed with a full stop: the words Automated patch release from main. The whole line, including the leading hyphen and space, is the string that the test compares byte-for-byte.

Version arithmetic. Only the third component changes, and it changes by exactly one. The first and second components are copied unchanged. For version 0.1.1 the result is 0.1.2. Conventional-commit interpretation, minor bumps and major bumps are out of scope, so the helper never inspects a commit message.

Git identity, commit and tag. The bump-and-tag job configures the committer and author name as github-actions[bot] and the email as github-actions[bot]@users.noreply.github.com. It stages exactly two paths, pubspec.yaml and CHANGELOG.md, and no others. The commit message is the whole of it: the word chore, then release in parentheses, then a colon, then a space, then the letter v followed by the new version. Nothing else, and in particular no skip instruction of any kind. That leading portion, the word chore with release in parentheses, a colon, a space and the letter v, is the release prefix the loop guard tests for, so the message the job writes and the condition the job checks are defined by the same sentence in this plan. The tag is annotated, never lightweight; its name is the letter v followed by the new version and its annotation message is the word Release followed by a space and the tag name.

Ordering and the tag-collision guard. After the helper prints the new version and before the commit is created, the job fetches tags and fails if a tag named after the new version already exists on the remote or locally. The commit is pushed to main first and the tag is pushed second, so that a rejected commit push, for instance because main moved during the run, leaves no tag and therefore triggers no publish. Nothing in either workflow ever deletes or force-pushes a tag or a branch.

What the publish workflow uses. The publish job delegates to the reusable workflow file named publish.yml in the .github/workflows directory of the dart-lang setup-dart repository, referenced at v1. It passes no secret and defines no publish command of its own, so the Dart-maintained workflow owns the SDK installation and the upload.

Operator gates, recorded as human prerequisites and not as repository files. Three items the research artifact leaves unresolved are configuration outside this repository and are planned as explicit gates, not guessed: whether automated publishing is enabled on the pub.dev admin tab for webmcp_flutter with repository owner and name ortal83cohen and flutter_webmcp and with a tag pattern of the letter v followed by the version placeholder; whether the RELEASE_GITHUB_TOKEN secret exists in the repository; and whether branch protection on main permits this token to push. Each workflow file states its prerequisite in a short English comment. The release job fails closed on the missing secret. The first release attempt made after this change is the point at which the other two gates are proved, and the implementer is not asked to prove them. A product document in the wiki records them during the document phase.

What is not touched. The existing .github/workflows/checks.yml file is not edited. The version in pubspec.yaml is not bumped by hand during implementation, and no tag is created during implementation, because the first bump is the automation's own first run.

## Risks

| Risk | Likelihood | Impact | Mitigation | Trigger that means it happened |
|---|---|---|---|---|
| The RELEASE_GITHUB_TOKEN secret is absent or expired | High | No release; possible half-finished git state if unguarded | Secret gate is the first step, before checkout and before any git write | The bump-and-tag job fails on its first step with the message naming the secret |
| Branch protection on main rejects the bot commit | Medium | Bump never lands; no tag, no publish | Commit is pushed before the tag, so a rejected push publishes nothing; operator gate recorded in the workflow comment | The push step fails with a protected-branch error and pub.dev shows no new version |
| Automated publishing is not yet enabled on pub.dev, or its tag pattern differs from the workflow pattern | Medium | Tag and commit land, publish job fails | Tag pattern fixed in this plan as the letter v plus three numeric components and named in the publish workflow comment; a failed publish can be retried by a later push once the pattern matches | The publish job fails on authentication while the tag exists on the repository |
| Two pushes to main land within the same minute and compute the same patch number | Medium | One run's push or tag is rejected | Non-cancelling concurrency group serialises the job, and the tag-collision guard fails the second run before it commits | A run fails at the tag-collision guard or at the tag push |
| The check suite passes on main but the published archive is still unwanted | Low | An unwanted version is permanent on pub.dev | The same tools/check.sh suite the repository already trusts gates the tag; nothing else can be added without re-validating | A version exists on pub.dev that the team wants gone |
| Every push to main produces a version, so trivial pushes consume version numbers and may approach pub.dev rate limits | High | Version-number noise; possible throttling | Accepted consequence of the chosen trigger; the research artifact marks the exact rate-limit numbers unverified, so the team avoids many releases in one day | A publish job fails with a rate-limit error, or the version number rises faster than the team expects |
| The bump commit re-triggers the release workflow | High, by design, because the secret-authenticated push does start runs | Runaway version bumps | The release-prefix condition on the job, which is the only guard and is tested by reading the same prefix out of the commit-message step | A release run appears whose head commit message begins with the release prefix, or version numbers rise with no human push between them |
| A skip instruction is added later to quieten the extra run, and it suppresses the tag-triggered publish | Medium, because the extra run looks like noise worth silencing | Every release bumps and tags but never publishes | The plan forbids any skip instruction in this automation's commit messages and states why; the loop guard needs no marker | A tag exists on main with no corresponding pub.dev version and no publish run in the Actions history |
| The publish job validates and uploads the archive on an SDK this repository does not pin | Medium | An archive accepted on a newer SDK than the one that gated the tag | The delegated Dart workflow owns SDK installation, and the repository's own constraint floor is checked by the check suite before the tag is created; the research artifact records the unpinned default | The publish job fails in its own dependency resolution or dry run while the check suite on the same commit passed |

## Rollback

Undoing the automation is deleting the two new workflow files, .github/workflows/release.yml and .github/workflows/publish.yml, and, if the helper is unwanted too, deleting tools/bump_patch_version.sh, tools/test_bump_patch_version.sh, the tools/fixtures/bump-patch-version directory and the stage that tools/check.sh added for the test. That returns the repository to its current behaviour, where releases are performed by a human. No data migration and no external state change is involved in that direction.

Publications already made are not reversible. A pub.dev version, once uploaded, is permanent; the research artifact records that a published package lasts forever and that 0.1.0 and 0.1.1 can never be reused. Retraction within seven days of publication is described in this work item's research file on automated publishing, and it is out of scope here: this plan neither builds nor documents a retraction path. Any version bump commit and tag that reached main can be reverted in git, but that changes nothing on pub.dev. This is therefore a one-way door for each version it publishes, and the team accepts that as the cost of the trigger the user chose.

## Out of scope

Conventional-commit interpretation for major or minor bumps. Publishing from pull requests or from any branch other than main. Bumping on feature branches. Creating GitHub Releases or release notes beyond the changelog section. A pub credentials JSON secret or any long-lived pub.dev credential. Editing .github/workflows/checks.yml. Synchronising the version into wiki documents. Renaming or re-scoping the package. Retracting or unpublishing a version. Proving that branch protection, the pub.dev admin setting or the repository secret already exist.

## Verification approach

The helper is checked by running tools/test_bump_patch_version.sh, which needs no network and no GitHub. Its positive cases assert the printed version, the rewritten pubspec version line and the exact new changelog heading and bullet, with the date pinned through the environment variable so the assertion is stable. Its negative cases assert a non-zero exit status and byte-identical fixture files for a two-component version, a version carrying a prerelease suffix, a changelog with no title line, a root with no changelog at all, and a fixture whose pubspec and changelog disagree because the changelog already documents the version the helper would compute.

The two workflow files are checked by reading them and by parsing them as YAML, asserting: the release trigger lists main and only main and declares no pull-request, dispatch or tag trigger; the concurrency group exists with cancellation disabled; the release-prefix loop guard is present on the job and tests the head commit message; the secret gate is the job's first step and names RELEASE_GITHUB_TOKEN; the Python and Flutter setup steps appear before the check-suite step; the check-suite step appears before the bump, commit, tag and push steps; the commit stages only the two files, its message begins with the release prefix and carries no skip instruction; the tag is annotated and named with a v prefix; each workflow carries its operator comment; the publish trigger is the v-plus-three-numbers tag pattern; the publish job references the dart-lang setup-dart reusable publish workflow at v1 and requests identity-token write; and neither file mentions any pub.dev credential.

Two of those assertions are cross-checks rather than single-file reads. The loop guard is checked against the commit-message step in the same file, so that the prefix the job writes and the prefix the condition rejects are one string. The Flutter version in the release workflow is checked against the version the existing checks workflow pins, so the tag is gated on the toolchain the repository already trusts.

The whole repository is checked by running the wiki lint and then the full check suite, whose final stage now includes the helper test. Finally, the implementation is checked for restraint: the diff must not modify .github/workflows/checks.yml, must leave the pubspec version at 0.1.1, must add no changelog section and must create no git tag. Each of these is a command whose output is pasted into the verification report.
