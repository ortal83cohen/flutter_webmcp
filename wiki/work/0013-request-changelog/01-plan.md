# Plan: Request-based release changelog

## Goal

Every new agent feature or change request has a durable file before work begins. Root-package deployment produces versioned changelog text exclusively from verified, undelivered request records, preserves the exact selection across retries, and marks delivery only after publication is proved.

## Approach

Introduce standard-library Python tooling for JSON records under `.changes/requests/`, immutable candidates under `.changes/releases/`, and immutable confirmations under `.changes/confirmations/`. Capture all requests, including internal and documentation changes. Record a sanitized English intent summary, never raw conversation, commit messages, or PR text. Public requests require a meaningful release note; internal requests require a classification reason and do not enter a public release. An internal-only batch is a successful no-op and remains available for audit without blocking later public releases.

Integrate capture into AGENTS.md, the workflow, and build, feature, and quick-change skills. Allocate the UUID and minimal numbered work item before routing or clarification. Multiple independently captured requests may link to one work item through an explicit request-ID list; each request has exactly one canonical work item. Promotion changes the route in the same work item and preserves request identities. Mandatory request and work bookkeeping does not count toward the quick-route one-product-file limit. Only existing route completion evidence permits pending requests to become ready; cancellation retains a reason and record.

Keep the current commit-then-tag publication order and add explicit recovery. A candidate freezes selected IDs, text, canonical record hashes, source tree, version and changelog digest in the same commit as pubspec and changelog changes. Unconfirmed candidates block new version allocation. Confirmation is a separate, append-only file committed to main after verifying the remote package identity and exact candidate payload. All release and confirmation writes use the same workflow concurrency group, fresh main reads, fast-forward pushes and bounded retries; a rejected push never authorizes overwriting intervening work.

## Why this approach

The [research](00-research.md) rejects commit/PR inference, mutable-only notes and reselecting on retry. JSON supports strict validation without a new runtime dependency. Separate reservations and confirmations distinguish intent from delivery. Internal-only no-op avoids manufactured release notes. Atomic ref updates remain unnecessary and unverified; existing commit-then-tag behavior gains an explicit repair path.

## Steps

1. Define the versioned schema, lifecycle commands and canonical JSON hashing in a new Python request module. Allocate unique UUID files exclusively and allocate numbered work folders with exclusive directory creation and retry. Preserve immutable summary, identity and creation time; permit note and evidence edits only before reservation. Keep lifecycle events with UTC timestamps and cancellation reasons. Produce deterministic errors without partial writes, using temporary files and a journal for multi-file local recovery.
2. Update workflow contracts, entry skills and templates to capture before routing, adopt an existing request ID when passed through another skill, retain identities on promotion and mark ready only after completion. Cancelled and awaiting-clarification work items may remain minimal, with explicit state and request backlinks. Document that an independent new request receives a new UUID even when added to an existing work item.
3. Extend lint with strict request, reservation and confirmation checks. Add a checked-in migration policy identifying the exact baseline tree and exempt legacy work IDs; all newly added work items require links. CI compares paths and record transitions against the trusted base tree: every non-bookkeeping changed path must be covered by a linked request's declared affected-path list. Reject deletion or immutable-field changes, orphan links, invalid lifecycle transitions, ambiguous duplicated JSON keys and duplicate IDs. Path coverage is structural evidence, not proof of semantic relevance.
4. Record legacy Unreleased text verbatim in a migration ledger with per-bullet disposition and evidence. Keep all existing numbered changelog sections byte-for-byte. Unresolved bullets block activation. Confirmed still-pending bullets require explicit new request records and readiness evidence; already-published bullets retain evidence in the ledger without reannouncement. Remove Unreleased text from the active changelog only after every disposition is established and preserved in the ledger. Never infer disposition from commits, PRs, local version numbers or heading order.
5. Replace generic note rendering in the bump helper through the new Python module, keeping its shell entry point. Select ready public records absent from every reservation; sort by fixed category order and then creation UTC and UUID. Use categories added, changed, fixed, removed, documentation and maintenance. Render trimmed single-line note text verbatim under category headings; reject blank text, line breaks and Markdown heading/control-character injection. No eligible public records means no files changed and no version or tag created. Validate every record even when none is eligible.
6. Freeze a candidate before any remote mutation. Store schema version, package, target version, release date, base commit and source-tree identity, selected IDs with exact note/category and full-record canonical SHA-256 hashes, plus rendered section digest. Prepare pubspec, changelog and reservation together; recover or roll back the local journal after injected write failure. Run required checks on the candidate. Commit the three files and push main before creating its tag; never publish a runner-local unpushed candidate.
7. Add a serial recovery operation keyed by version. If the release commit is durable but the tag is absent, verify the reservation and release commit on main and create only that tag. If the tag exists, require it to resolve to that exact release commit. New ready requests wait. A stale pre-push run discards its unpublished preparation, reloads main and reruns checks and selection; it first detects any durable unconfirmed candidate and switches to recovery. Bound retries and fail visibly without forcing refs.
8. Extend publish handling to inspect the existing remote package version before upload. Absent means retry the original tag-triggered publication after exact payload validation; present means verify identity and reconcile without uploading. Persist a confirmation only when package name, version, registry archive checksum and a normalized archive file-path/content-digest manifest match the candidate's exact validated publish payload. Normalize archive container metadata only, not file content. Bind confirmation to reservation digest, release commit/tag identity, registry URL, archive digest, payload digest and confirmation UTC. A mismatch or ambiguous registry/network response leaves the candidate pending and blocks new releases.
9. Persist confirmations through a fresh-main fast-forward commit containing only the new confirmation file. On push rejection, reread and validate main, preserve the same confirmation identity and retry without changing its candidate. An identical existing confirmation is success; conflicting proof is an error. If publication succeeded but local proof was lost, rebuild the exact tagged payload and compare with the remote archive before writing confirmation. Keep credentials out of records. A dedicated confirmation path-only run is a successful no-op; an optional release-message loop guard is operational only and never a note source.
10. Test isolated filesystem and Git-remote fixtures, including every interruption boundary, then run the full repository suite and independent implementation review. Update product documentation and an ADR in the implementation change. Before activation, separately prove registry identity matching, original tag-run recovery, confirmation write permission and exact dry-run exclusions. Until these gates pass keep the new publishing path disabled; no current planning authorization permits live publication.

## Interfaces and shared decisions

Request filenames are canonical UUIDs with a JSON suffix. Required fields are schema version, matching ID, immutable sanitized English summary, creation UTC, canonical work-item path, public or internal visibility, classification reason, category, public release note when applicable, pending/ready/cancelled status, affected repository paths and lifecycle/evidence references. Evidence references identify completion artifacts and check commands/results; lint checks their structure and route gates, while fresh checks establish current validity. Reserved records are frozen in full. Delivered is derived exclusively from a valid confirmation, never a fourth editable request status.

Release and confirmation filenames use the exact root package version. The initial version rule remains patch increment; duplicate headings, reservations, conflicting package/version identities and cross-version reuse of request IDs fail closed. A source snapshot is the pre-release Git tree plus exact candidate file digests; the release commit is resolved by the tag and confirmation, avoiding a self-referential commit hash in its own manifest. Full-record hashes use a documented canonical UTF-8 JSON serialization and SHA-256. The publisher binds the resulting tagged archive to that reservation through its normalized payload manifest.

The shared concurrency group serializes automated state transitions across release, publication and reconciliation. Human pushes are handled by fast-forward rejection and fresh reads. No job waits inside that group for a second job needing the same group; durable state hands off between jobs. A pending candidate takes precedence over any newer request selection. All tooling input for note text is checked-in request JSON only. Git paths, hashes and refs are allowed for integrity, coverage and transport, never for prose generation. `.pubignore` excludes all `.changes/` material; the archive still includes generated public CHANGELOG.md.

## Risks

| Risk | Likelihood | Impact | Mitigation | Trigger that means it happened |
|---|---|---|---|---|
| Publication succeeded but confirmation disappeared | Medium | Duplicate delivery claim | Reconcile remote exact payload before confirmation; never re-bump | Existing remote version with no confirmation |
| Main advances during write | Medium | Lost work or stale selection | Fast-forward only, reread and bounded retry | Push rejected |
| Legacy release mapping unknown | High | False release history | Fail-closed disposition ledger | Any unresolved legacy bullet |
| Request contains sensitive text | Medium | Repository disclosure | Sanitized intent only and review; exclude metadata from archive | Secret/raw-chat fixture accepted |
| Trusted publishing retry contract differs | Unknown | Candidate remains blocked | Controlled integration gate before activation | Same-tag rerun cannot authenticate |
| CI coverage overclaimed | Medium | Uncaptured requests invisible | Document observable structural scope | Claims of conversational completeness |

## Rollback

Disable new release and publish automation while retaining every request, reservation, confirmation and legacy ledger. Revert executable integration and workflow changes through a reviewed change without deleting evidence or altering existing tags, package versions or numbered changelog history. An unconfirmed candidate remains blocked for reconciliation; rollback must not restore generic automatic releases or imply publication was undone. Fix an already-published defect through a new explicit request and later version.

## Out of scope

Implementation or live publishing during this planning task; nested-package releases; historical numbered-note reconstruction; semantic-version policy changes beyond the existing patch rule; raw conversation storage; commit/PR note extraction; proving unseen conversations were captured; moving existing tags.

## Verification approach

Use deterministic Python and shell fixtures with synthetic requests, temporary repositories and a simulated registry to exercise positive, negative, retry and race cases in the criteria. Record exact outputs from wiki lint and the full repository check during implementation verification. Local simulations do not establish hosted CI, publisher trust or real registry behavior; collect those separate activation proofs before enabling the path.

## Final scope amendment — 2026-09-11

This amendment supersedes the internal-request exclusion in Approach, Why this approach, Step 5 and Interfaces and shared decisions. The final effective contract includes every ready, unreserved request in the next candidate, including internal, documentation and maintenance work. Every request requires a sanitized meaningful release note suitable for the public changelog. Visibility and classification affect categorization and presentation only; they never exclude an otherwise eligible request. An internal-only ready batch therefore creates a release containing those explicit notes, never a generic maintenance bullet.

The successful no-op applies only when there are zero ready, unreserved requests after validating all records. Existing reservation and confirmation rules still prevent duplicate delivery. Rendering, privacy review, deterministic ordering, schema validation and empty-note rejection apply equally to every classification. Step 1 must enforce the note requirement for all requests, and Step 5 must select without a visibility filter. No other design, recovery rule, migration gate or authorization boundary changes.
