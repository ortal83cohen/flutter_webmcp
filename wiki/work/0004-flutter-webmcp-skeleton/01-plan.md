# Plan: Flutter WebMCP package skeleton

## Goal

After this change the repository contains a working, self-checking Flutter package skeleton: a named Dart package rooted at the repository root, a singleton tool registry, an optional widget-lifecycle layer that lets a screen and the buttons inside it opt in to tool exposure with one line each, a runnable Flutter web example that registers tools both imperatively and through that layer, a test suite that has been demonstrated to report failure, a committed formatter and analyzer configuration, one documented command that runs the whole check suite end to end, and a CI workflow that runs that same command alongside the existing wiki lint. An engineer cloning the repository can run one command and see every stage pass, and can run the example in Chrome and see the registered tool names and the active transport identifier on screen. The browser's WebMCP API is not called anywhere; the skeleton stops at a detection-and-log seam.

## Approach

The package is rooted at the repository root, not in a subfolder. `pubspec.yaml`, `analysis_options.yaml`, `lib/`, `test/` and `example/` sit beside the existing `wiki/`, `tools/` and agent configuration. The package name is `webmcp_pilot`, confirmed unclaimed on pub.dev as of 2026-09-05 (the package page returns HTTP 404), so this is a settled fact rather than a runtime decision any step needs to make — every file, path and criterion in this plan names the package `webmcp_pilot` directly. Rooting the package at the repository root is what makes the root `README.md` the package's pub.dev README, which is why the README edit in step 10 inserts the package section *above* the existing scaffold content rather than appending below it.

The Dart side is a plain singleton registry with no widget-tree dependency, per the research artifact's registry finding. A single public library file, `lib/webmcp_pilot.dart`, exports the whole public surface; everything else lives under `lib/src/` and is never imported directly by a consumer or by the package's own public-surface test. The registry holds a name-keyed map of tool descriptors, validates tool names against the spec's character rule, rejects duplicates, dispatches invocations to the registered handler, and notifies a transport on every registration change. A second, deliberately minimal extension point, a tool-source interface, exists so the later `go_router` adapter is additive rather than a change to the registry: a source returns a list of tools and the registry registers them through the same validating path.

On top of that singleton — never inside it — sits an optional widget-lifecycle layer, the research artifact's "option C" hybrid, made concrete here. It is three types and nothing more. `WebMcpScope` is a plain Dart object that owns a set of tool names, adds them through the registry's ordinary `registerTool` path and removes them through `unregisterTool`; it imports no Flutter library and is unit-testable without pumping a widget tree. `WebMcpScreen` is a mixin applied to a `State` subclass: it creates a scope in `initState`, offers an overridable hook where the screen declares tools that have no widget of their own, and closes the scope in `dispose`. `WebMcpAction` is a stateful wrapper widget that takes a tool name, a description, an optional input schema, an explicit invocation callback and a child; it finds the nearest enclosing `WebMcpScreen`'s scope, adds its tool once when it is mounted, removes it when it is unmounted, and returns its child from `build` unchanged so it changes nothing about rendering, layout or hit testing. The registry gains no method, no field and no `BuildContext`; the layer is pure composition over the seven public operations that already exist.

Platform isolation is a conditional export, named explicitly here so no step has to guess. The file `lib/src/transport/transport_selector.dart` exports the non-web implementation by default and the web implementation when the compile-time constant `dart.library.js_interop` is available. Both implementation files declare the same top-level factory function, and every other file in the package imports only the selector. The web implementation performs feature detection with the presence check from `dart:js_interop_unsafe`, called directly against `document` with the string key `'modelContext'`, and writes one log line per event; it never reads the `modelContext` getter's value and never calls a browser method. No separate interop-extension file exists in this work item: a typed `external` getter on `package:web`'s `Document` type is only worth adding once a later work item actually reads or calls through it, and adding one now would sit in `lib/` unused by anything and unchecked by any criterion. The widget-lifecycle layer changes none of this: it registers Dart-side descriptors and nothing else, so the transport stays detection-only and `document.modelContext` is still never called from any file in this work item.

The analyzer binary for this repository is **`dart analyze`**, invoked exactly once from the repository root by the check script and by CI. This is a deliberate, single decision that every step, the check script and every acceptance criterion is written against; the reasoning is in the next section, alongside the separate and more important decision about what the two committed `analysis_options.yaml` files must already contain before any command runs. The check script is `tools/check.sh`, a POSIX shell script with a preflight and six numbered stages — wiki lint, dependency resolution, format check, static analysis, tests, web build — in that fixed order, aborting at the first failing stage and naming it. `AGENTS.md` gains a `## Checks` section naming that script as the full-suite command, so every later pipeline phase runs what CI runs.

## Why this approach

**Why the analysis-options files are committed pre-migrated, and why that is the actual fix, not the choice of analyzer binary.** The Flutter SDK ships a one-time migration, `AnalysisOptionsMigration`, that runs inside `FlutterProject.ensureReadyForPlatformSpecificTooling` — reached by `flutter pub get` for both the root project and `example/`, and by every command routed through `FlutterCommand.verifyThenRunCommand`, which is most Flutter commands including `flutter test` and `flutter analyze`. It checks whether the file's `analyzer.exclude` list already contains all seven of `build/**`, `android/**`, `ios/**`, `web/**`, `windows/**`, `macos/**`, `linux/**`; if any is missing, it rewrites the file in place and prints "Upgrading analysis_options.yaml to exclude build and platform directories." `dart analyze` does not run this migration, because it never constructs a `FlutterProject` — but the check script's dependency and test stages run `flutter pub get` and `flutter test`, both of which do, so choosing `dart analyze` for the analysis stage alone would not have prevented a first-run mutation of a committed file. The actual fix is upstream of the binary choice: both committed `analysis_options.yaml` files list all seven required entries from the moment they are written (step 2), so the migration's own check finds nothing missing and never fires, for any command, on any stage, from the first run onward. `dart analyze` is still the analysis stage's binary, chosen because it needs no `FlutterProject` context for a plain static-analysis pass and keeps the analysis stage's dependency surface smaller than routing it through the Flutter command runner — a real but secondary reason, no longer the load-bearing one.

**Explicit exclusions over tool defaults, stated once and owned per file.** The analysis stage's scope is a fixed list of what is and is not analyzed, stated in the Interfaces section. `example/analysis_options.yaml` owns the exclusion for `example/build/` — the directory the build stage creates — because that is the file whose analysis context actually covers it; the root file's own exclusion list is for the root tree, which has no `build/` of its own to exclude beyond what `.gitignore`-style patterns already keep untracked. Neither exclusion list is inherited from a tool default or written by a migration; both are authored in step 2 and never touched again by any later command.

**Singleton registry over a widget-based one, with the widget layer strictly on top.** Taken from the research artifact's registry finding: a widget-based *registry* cannot be unit-tested without pumping a tree, gains nothing for router introspection, and carries a `BuildContext` dependency that a future non-Flutter consumer would have to strip. That decision is unchanged by this revision. What this revision adds is the research artifact's own "option C": the singleton stays the single source of truth, and the widget-lifecycle layer is sugar that calls its existing public methods. The separation is not merely asserted, it is enforced mechanically — the repository-hygiene test fails if any Dart file under `lib/` outside the single directory `lib/src/widgets/` imports a `package:flutter/` library, so the registry, the descriptor, the exceptions, the scope and the whole transport seam are provably free of a widget dependency and could be split into a Flutter-free companion library later without moving a line of logic.

**Why an ancestor-`State` lookup rather than an `InheritedWidget`.** `WebMcpAction` has to find the scope its enclosing screen created. An `InheritedWidget` would require the screen's own `build` to wrap its returned subtree in a provider widget, which is exactly the per-screen boilerplate the mixin exists to remove, and it would buy the one thing this layer never needs: rebuilding descendants when the provided value changes. A scope object's identity does not change for the life of the `State`, so there is nothing to depend on. The nearest-ancestor-`State` lookup gives the same reach with zero lines in the screen's `build`. This is a lifetime lookup, not a resolution rule: the same tool name never resolves differently depending on which screen is nearest, because the layer registers names verbatim into the one flat namespace the registry already owns. Per-screen shadowing stays decided against, as before.

**Why an explicit invocation callback rather than reusing the child's `onPressed`.** The tempting version of `WebMcpAction` reads the child button's `onPressed` and exposes it as the tool handler, so a wrapped button needs no callback at all. It is rejected for four independent reasons, any one of which is sufficient. First, it only works by type-testing a closed, open-ended list of widget classes — `ElevatedButton`, `TextButton`, `IconButton`, `InkWell`, `GestureDetector`, every custom button in every app — and silently exposes a tool with no behaviour for anything not on the list. Second, it only works when the wrapper's immediate child *is* the button; a `Padding` or an `Align` between them breaks it, silently. Third, the signatures do not match: a button callback takes no arguments and returns nothing, while a tool handler receives an argument map and returns a value, so a synthesized handler could never express a tool that has an input schema — the layer would be permanently limited to zero-argument tools. Fourth, a silently synthesized tool is a safety problem in a package whose entire purpose is exposing app capability to an external agent: what the agent can invoke must be what the developer wrote down, not what the package inferred. The supported idiom for the "I already have an `onPressed`" case is stated plainly in the Interfaces section and in the README usage paragraph: hoist the callback into a named method and pass it to both the button and the wrapper. The package never inspects the child.

**Why the tool-source interface is not the extension point for this layer.** `WebMcpToolSource` declares one method returning a list of descriptors, consumed once by `registerSource`. It is a pull-once, no-lifetime contract: it has no unregistration, no ownership tracking and no notion of a tool appearing later. The widget layer needs the opposite on every axis — each `WebMcpAction` mounts independently and after its screen, so a screen asked for its full descriptor list in `initState` could not answer, its children not having been built yet. Making the screen a source would therefore either register nothing or force the screen to duplicate, by hand, the list its own subtree already declares. The two mechanisms are kept distinct and joined at one point instead: the scope accepts a `WebMcpToolSource` and adds every descriptor it returns under the scope's ownership, so an app that already has a source object gets lifetime management for free without either interface changing. The source interface stays the batch-declaration extension point for the later router adapter; the scope adds lifetime to whatever is added through it.

**Detection-only web transport over a real browser call.** WebMCP is a Community Group draft in a Chrome-only origin trial whose lifecycle details have already changed release over release. Calling it from the skeleton would put an unstable, un-unit-testable dependency in the critical path of the first check suite. The seam costs one interface and two implementations; the call itself is a later work item. The widget layer does not change this: it produces and removes Dart-side registrations, which the transport observes through the notification methods it already has.

**No committed lock files over a lock file plus a version-pin file.** A published library package resolves against ranges, and the example is not a deployed application, so nothing is gained by committing either lock file — and without a committed lock file there is no artifact for CI's installed Flutter version to drift from. The Flutter version is therefore pinned in exactly one place, a single literal in the CI workflow's package job, and the job prints the resolved version so the pin is observable in the log. A separate pin file was considered and rejected: it would add a second file whose format and reader both had to be specified to be worth anything, for no benefit over a single literal that is already the thing CI reads directly.

**Unresolved research items, and why none blocks this plan.** The research artifact leaves eight items open. The Chrome testing-flag question and the `outputSchema` mechanism are moot because no browser call is made here. Per-screen tool shadowing is *decided* by this plan rather than left open: the skeleton has one flat tool namespace and no shadowing, and the widget layer added by this revision deliberately does not introduce one — a scope is a lifetime grouping, not a resolution namespace. The capability diff against the competing packages and the third prior-art package are prerequisites for the publishing work item, and publishing is out of scope; note that the competing `flutter_webmcp` package already ships a scope widget, which is a differentiation question for that later work item, not a blocker here. Whether `dart-lang/web` plans to ship `modelContext` affects no file in this work item, since the presence check calls `dart:js_interop_unsafe` directly by string key rather than through a typed extension getter. The pana rule text on deprecated interop libraries is moot because the hygiene test forbids those imports outright regardless of how pana scores them. The maintenance status of the reference JavaScript toolkit affects no file here. No open item blocks a decision this plan makes.

## Interfaces and shared decisions

**Package identity.** Name `webmcp_pilot`, version `0.1.0`, description one sentence between sixty and one hundred eighty characters naming WebMCP and Flutter web. The `repository` and `homepage` fields are omitted from `pubspec.yaml` in this work item. This repository's `origin` remote (`https://github.com/ortal83cohen/project-AI-skeleton`) is, mechanically, where this package's source currently lives, and pub's `repository` field records exactly that — so the field is not deferred because the URL would be factually wrong, but because whether this shared, multi-purpose scaffold repository is the package's permanent public home is a publishing-time decision this skeleton does not make. Writing the field now would assert that decision has been taken when it has not. Settling it is a prerequisite for the publishing work item, recorded there as a follow-up, not decided here. The `environment` Dart constraint's lower bound is the Dart version bundled with the pinned Flutter release, and never below 3.4 because `package:web` requires it. Dependencies: the Flutter SDK, and `package:web` at a caret range whose lower bound is 1.1.1. Development dependencies: `flutter_test` from the SDK and `flutter_lints` at a caret range. A `platforms` map declares web and nothing else. The widget-lifecycle layer adds no dependency and changes no manifest field: the package already depends on the Flutter SDK, so exporting two widget-tree types from the same public library changes neither the dependency set nor the declared platform. The example manifest declares name `webmcp_pilot_example`, `publish_to` set to none — omitting it makes a path-dependency example produce an invalid-dependency analyzer warning that fails a fatal-infos run — a relative path dependency on the root package, the Flutter SDK, `flutter_test` and `flutter_lints`, and no `platforms` map.

**Public surface.** `lib/webmcp_pilot.dart` exports: the `WebMcp` class, the `WebMcpTool` descriptor, the `WebMcpToolHandler` function type, the `WebMcpToolSource` interface, the `WebMcpTransport` interface, the `WebMcpScope` class, the `WebMcpScreen` mixin, the `WebMcpAction` widget, and the five exception types. It contains export directives only and no import directive, so it stays inside the Flutter-import hygiene rule below even though two of the things it exports do depend on Flutter. `WebMcp` is a singleton reached through a static `instance` getter with a private constructor. Its seven public operations are unchanged by this revision: `registerTool` taking a descriptor; `registerSource` taking a source and registering every tool the source returns through the same validating path as `registerTool`; `unregisterTool` taking a name and returning a boolean, true when a tool was removed and false when no tool of that name was registered, never throwing for an absent name; `tools`, returning an unmodifiable list of descriptors sorted ascending by name; `invokeTool`, taking a name and an argument map and returning a future of a nullable object; `reset`, taking an optional transport, which clears all registrations and installs either the given transport or a freshly created default one; and `transportId`, a synchronous string getter naming the active transport. The widget layer adds no eighth operation and no parameter to any of the seven.

**Data shapes.** `WebMcpTool` is an immutable class with a `name` string, a `description` string, an `inputSchema` map from string to nullable object stored as an unmodifiable copy and defaulting to empty, and a `handler`. `WebMcpToolHandler` takes an argument map from string to nullable object and returns a future-or of a nullable object. `WebMcpToolSource` declares one method returning a list of descriptors. There is no runtime configuration: no environment variables, no configuration file, no constructor parameters other than those named here.

**Error handling.** One abstract base, `WebMcpException`, implementing `Exception`, carrying a message and a tool name, whose string form begins with the concrete class name and includes the tool name. Four concrete subtypes: `WebMcpInvalidToolNameException`, thrown by registration when a name is not between one and one hundred twenty-eight characters drawn from ASCII letters, digits, underscore, hyphen and period; `WebMcpDuplicateToolException`, thrown by registration when the name is already registered, leaving the existing registration untouched; `WebMcpToolNotFoundException`, thrown by invocation when no tool of that name is registered, without invoking any other handler; and `WebMcpScopeMissingException`, thrown by `WebMcpAction` when it is mounted with no enclosing `WebMcpScreen` scope, carrying the tool name it was going to register. Exceptions thrown by a tool handler propagate to the caller of `invokeTool` unwrapped and unlogged. All five types live in `lib/src/webmcp_exceptions.dart` even though the fifth is only ever thrown from a file under `lib/src/widgets/`, so the exceptions file has one owner and one export line.

**Transport seam.** `WebMcpTransport` declares a string `id` getter and two void notification methods, one for registration and one for unregistration. The non-web implementation is `NoopTransport` with identifier `noop` and empty methods; it logs nothing. The web implementation is `WebDetectionTransport` with identifier `web-detection`; on construction it records whether the document object has a `modelContext` property, checked via `dart:js_interop_unsafe`'s `hasProperty`/`has` called directly against `document` with the string key `'modelContext'` (no typed getter is declared for this — see Approach), and writes one line per construction and per notification through `dart:developer`'s log with the logger name `webmcp_pilot`, each line containing the exact substring `not published`. It never reads the `modelContext` value and never calls a method on it. `lib/src/transport/transport_selector.dart` is the conditional export: the non-web file by default, the web file when `dart.library.js_interop` is available. Both files declare a top-level factory function `createDefaultTransport` returning a `WebMcpTransport`. No file outside the selector imports either implementation. Registrations made through the widget layer reach the transport by the same two notification methods, because the layer registers through `registerTool` and `unregisterTool` and by no other path.

**Widget-lifecycle layer: `WebMcpScope`.** A plain Dart class in `lib/src/webmcp_scope.dart`, importing the registry, the descriptor, the source interface and `dart:developer`, and importing no Flutter library. Constructed with one required `scopeName` string used only in log lines and in the object's string form; it is never combined with, prefixed to, or otherwise allowed to influence any tool name. The scope always operates on `WebMcp.instance`; no registry is injectable, because the registry's constructor is private and this revision does not change it — tests isolate scopes by calling `reset` between cases, as the existing registry tests already do. Members: `addTool`, taking a descriptor and returning a boolean, true when the scope now owns that name and false when the name was already registered by someone else; `addSource`, taking a `WebMcpToolSource` and passing each descriptor it returns through `addTool`, returning nothing; `removeTool`, taking a name and returning a boolean, removing the tool from the registry only if this scope owns that name and otherwise doing nothing and returning false; `ownedNames`, an unmodifiable list sorted ascending; `skippedNames`, an unmodifiable list sorted ascending of names this scope attempted and did not get; `isClosed`; and `close`, which removes every name the scope still owns, empties both lists and marks the scope closed. Failure behaviour is split by cause and the split is deliberate: a condition a correct application can hit at runtime is absorbed and made observable, while an authoring error is left to propagate loudly. Concretely, a `WebMcpDuplicateToolException` from the registry is caught inside `addTool`, the name is appended to `skippedNames`, one line is logged through `dart:developer` with logger name `webmcp_pilot` naming the tool and the scope, and false is returned — the existing registration and its owner are untouched, which is why `removeTool` and `close` are ownership-limited. No criterion depends on that log line's wording; `skippedNames` is the observable the tests read. A `WebMcpInvalidToolNameException` is not caught and propagates to the caller, because an invalid name is always a source-code defect and swallowing it would leave a tool permanently and silently absent. `close` is idempotent: a second call removes nothing and throws nothing. Calling `addTool` or `addSource` on a closed scope throws a plain Dart `StateError`, the idiomatic use-after-disposal signal, rather than a sixth package exception type.

**Widget-lifecycle layer: `WebMcpScreen`.** A mixin in `lib/src/widgets/webmcp_screen.dart` whose `on` clause is Flutter's `State` class parameterised by `StatefulWidget`, so it is applied to the `State` subclass and not to the `StatefulWidget` subclass. This is stated explicitly because the requested shape was a mixin on the widget class: a `StatefulWidget` has no `initState` and no `dispose` — the lifecycle this layer needs lives on `State` — so the mixin goes on the state class and the widget class is left untouched. The mixin overrides `initState`, calling the superclass implementation first, then creating its `WebMcpScope` with a scope name derived from the state object's runtime type for logging only, then calling `registerWebMcpTools`, an overridable method whose default implementation is empty and which is where a screen declares tools that have no widget of their own. It overrides `dispose` to close the scope and then call the superclass implementation last. It exposes the scope through a `mcpScope` getter, non-null between `initState` and `dispose`. It declares one static method, `maybeScopeOf`, taking a `BuildContext` and returning a nullable `WebMcpScope` by looking up the nearest ancestor `State` that has this mixin; there is deliberately no non-nullable `scopeOf`, because the only caller that needs to fail on absence is `WebMcpAction`, which throws `WebMcpScopeMissingException` carrying its own tool name — a name a bare lookup helper would not have.

**Widget-lifecycle layer: `WebMcpAction`.** A `StatefulWidget` in `lib/src/widgets/webmcp_action.dart`, importing `package:flutter/widgets.dart` and not `package:flutter/material.dart`, so the package never forces Material on a consumer. Constructor parameters: an optional `key`; a required `name` string, registered verbatim as the tool name with no prefix, suffix or derivation of any kind; a required `description` string; an optional `inputSchema` map defaulting to empty, with the same shape and copying rule as the descriptor's; a required `onInvoke` of the exported `WebMcpToolHandler` type; and a required `child` widget. Its `build` returns that child unchanged and adds no widget, no render object and no gesture handling, so wrapping a button cannot change how the button looks, lays out or responds to a tap. It never reads, type-tests or copies the child — see the rejected alternative above for why the child's own callback is not reused. Its state registers exactly once, on the first call to `didChangeDependencies` rather than in `initState`, because that is where an ancestor lookup is unambiguously legal and it still runs after the enclosing screen's `initState` and before the first paint; a boolean guard makes it once-only. Registration builds a descriptor whose handler is a stable forwarder owned by the state object, which calls the *current* widget's `onInvoke` at invocation time — so a rebuild that supplies a new closure over new state is picked up, while a closure captured at mount time would go stale, which is the single most likely defect in this layer. The rest of the descriptor is captured once: changing `name`, `description` or `inputSchema` on an already-registered element has no effect until that element is replaced, and `didUpdateWidget` is deliberately not overridden. The state calls `WebMcpScreen.maybeScopeOf` and throws `WebMcpScopeMissingException` naming its tool if the result is null; otherwise it calls the scope's `addTool` and remembers whether it got ownership. In `dispose` it calls the scope's `removeTool` with its name only if it got ownership, so an action whose name was skipped as a duplicate cannot remove the tool that beat it, and then calls the superclass implementation. There is no `enabled` parameter: a screen that wants a tool exposed conditionally omits the `WebMcpAction` from its `build`, and the mount/unmount path already registers and removes it — adding an `enabled` flag would mean a second, parallel registration path driven by `didUpdateWidget`, for no capability the first path lacks.

**Namespace and collision rules for the layer, stated once.** There is one flat tool namespace, owned by the registry. A scope is a lifetime grouping, not a resolution namespace: it never renames, prefixes or shadows. Two live screens exposing the same literal tool name is therefore a collision, not a shadowing opportunity — the first registration wins and stays reachable, the second is recorded in `skippedNames` and owns nothing, and neither screen's teardown can remove the other's tool. The duplicate exception thrown by the registry is reused unchanged; no new duplicate-handling type is introduced.

**Check stages.** `tools/check.sh` runs a preflight that fails with a message naming the missing binary if either `flutter` or `dart` is absent from the path, then six stages in this fixed order: (1) wiki lint, running `python3 tools/lint_wiki.py`; (2) dependencies, running `flutter pub get` at the root and then inside `example/`; (3) format, running the Dart formatter in check-only, exit-if-changed mode over exactly the four paths `lib`, `test`, `example/lib` and `example/test`, never over the repository root, so generated output is never inspected; (4) analysis, running `dart analyze` once from the repository root with infos and warnings both made fatal by explicit flags; (5) tests, running `flutter test` at the root and then inside `example/`; (6) build, running `flutter build web` inside `example/`. Each stage prints one line naming the stage number and its outcome. The script aborts at the first failing stage and exits non-zero. The new files under `lib/src/widgets/`, the two new root test files and the new example screen fall inside the four format paths and the analysis scope already listed here, so no stage's path list changes.

**Analysis scope, stated without relying on any tool default.** Analyzed: every Dart file under `lib/`, `test/`, `example/lib/`, `example/test/` and any other tracked Dart file under the repository root. Not analyzed: everything under `example/build/`, excluded by an entry in `example/analysis_options.yaml` naming that directory relative to its own location (with a second, redundant `example/build/**` entry in the root file as a safeguard); everything under either package's own `.dart_tool` directory, excluded by an explicit `.dart_tool/**` entry written into both options files, not by the analyzer's hidden-directory default; and nothing else. The root file's `analyzer.exclude` list carries nine entries: the seven `AnalysisOptionsMigration` requires (`build/**`, `android/**`, `ios/**`, `web/**`, `windows/**`, `macos/**`, `linux/**`), plus `example/build/**` and `.dart_tool/**`. The example file's list carries eight: the same seven required entries, plus `build/**` and `.dart_tool/**` written relative to its own location — it does not repeat `example/build/**`, which only has meaning relative to the root. Either way, the migration finds all seven required entries already present in both files and never has anything to add; the entry that actually governs analysis of files under `example/` is the one in `example/analysis_options.yaml`. The root options file includes the `flutter_lints` rule set and additionally requires documentation comments on public members — which applies to `WebMcpScope`, `WebMcpScreen`, `WebMcpAction` and their public members exactly as it does to the registry's; the example's options file includes `flutter_lints` only, deliberately relaxed, since example code is not published API.

**Forbidden import list, Flutter-import rule and secret-token list.** `test/repo_hygiene_test.dart` fails if any Dart file under `lib/` or `example/lib/` imports `dart:html`, `dart:js`, `package:js`, `dart:io` or `package:http`. It fails if any Dart file under `lib/` whose path is not inside `lib/src/widgets/` contains an import directive whose URI begins with `package:flutter/` — export directives are not import directives, so the public library's export lines are outside this rule by construction, and this is the mechanical guarantee that the registry, descriptor, source interface, exceptions, scope and transport seam stay free of a widget-tree dependency. It fails if the public-surface test imports anything under `lib/src/`, and if `test/webmcp_scope_test.dart` imports anything from `package:flutter_test/`. And it fails if any file under `lib/`, `example/lib/`, `tools/` or `.github/` contains any of the fixed literal markers for a private-key header, an AWS access-key prefix, or the words for an application key or a password used as an assignment target. All four lists are fixed here so no step invents its own.

**Documented commands.** `AGENTS.md`'s `## Checks` section names exactly four, and the full-suite command is the fixed literal `bash tools/check.sh` — chosen over `./tools/check.sh` or a bare `tools/check.sh` so the command is correct regardless of the executable bit or the invoking shell's configuration, and named identically, character for character, in `AGENTS.md` and in the CI workflow step, since AC-025 checks the two strings for exact equality. The other three: a single test is the Flutter test runner given one file path; format is the Dart formatter over the same four source paths the format stage checks — `lib`, `test`, `example/lib` and `example/test` — never the repository root; analyze is `dart analyze` with the fatal flags from the repository root. The CI package job runs `bash tools/check.sh` verbatim, as one step.

## Rollback

Every change is either a new file or one of four edits to existing files: `README.md`, `AGENTS.md`, `.gitignore` and `.github/workflows/checks.yml`. Reverting the implementation commit restores all four to their present contents and deletes the new files. There is no database, no schema, no migration, no deployed service and no published artifact, so nothing outside the repository depends on the change. The widget-lifecycle layer is the most cleanly reversible part of the change on its own: it is three new files under `lib/`, two new test files, one new example file and eight export lines, and because the registry has no knowledge of it, deleting those files and those lines returns the package to the singleton-only shape without touching a line of registry logic.

Two things a revert does *not* undo, stated plainly. First, network side effects already performed: every dependency-resolution and build stage contacts the package server and the SDK artifact host, downloading packages into the machine-local pub cache; the cache entries survive the revert, though they are inert, so the claim "no external service is contacted" would be false and is not made. Second, if a human explicitly authorizes it, any branch pushed to the remote to observe CI stays in the remote's history along with its Actions run and logs until someone deletes the branch explicitly, and reverting a local commit does not remove it — but step 11's completion condition does not require that push (see step 11 and AC-026), so this cost is incurred only if and when that separate authorization is given, not as part of finishing this work item. The pub.dev name is not claimed by this work item because nothing is published, so the name remains freely changeable here; it becomes a genuine one-way door only in the later publishing work item, which is out of scope.

No step in this plan is a one-way door. One item nonetheless needs a human before it hardens: the licence and its copyright holder.

## Out of scope

Calling the browser's WebMCP API at all — registration, discovery, execution, the `toolchange` event and the `AbortSignal` unregistration mechanism are all deferred, including for tools registered through the widget layer, which produce Dart-side registrations and nothing else. The `go_router` adapter and navigation-tool generation: only the tool-source interface exists here, with no implementation. The dev-time non-browser transport: only the transport interface exists here. Automatic tool discovery: nothing in this work item walks a widget tree looking for buttons to expose, and no tool is ever registered that the developer did not name in source — the layer is opt-in per screen and per action by construction. An `enabled` or otherwise conditional-exposure parameter on the wrapper, and any registration path driven by `didUpdateWidget`. Per-screen tool shadowing — this plan decides against it, and the scope introduced here is a lifetime grouping that deliberately does not provide it. Publishing to pub.dev, running pana, and the capability diff against the competing packages. A `repository`/`homepage` field in `pubspec.yaml` naming this package's own eventual repository location. The declarative form-annotation API, which the research artifact already rules inapplicable. Typed input decoding and output schemas. Browser-based integration or end-to-end tests. Support for any platform other than web. Community-health files beyond the licence and changelog. Any change to the existing wiki job in the CI workflow, to the existing wiki content, or to the agent configuration other than the `## Checks` section added to `AGENTS.md`.

## Verification approach

Every acceptance criterion in `02-criteria.md` is checked in one of four ways, and each criterion's negative case is a concrete mutation applied to the working tree, one at a time, reverted immediately after the observation, with `git status --porcelain` empty again before the next one is applied.

Most criteria are exit-code checks: run `tools/check.sh`, or one named stage of it, and read the exit status and the stage lines. The registry, scope, transport, hygiene and example-tool criteria are covered by the seven named test files from step 6 and the one from step 7, and are exercised by the test stage. The widget-layer criteria are covered by exactly one file, `test/widget_layer_test.dart`, which is the only place in the suite that pumps a widget tree; its fixtures — a host screen whose state mixes in the mixin, a second host screen used only for the duplicate case, and a counter holder the wrapped button and the tool handler both write to — are defined inside that test file and exist nowhere else. `test/webmcp_scope_test.dart` covers the same layer's non-widget half with no tree at all, and the hygiene test asserts that it stays that way. Three checks are not exit-code based and are named here so no one expects a command for them: the README criterion is checked by reading the diff and confirming that every insertion sits above the previously-first line and that the ADR-referenced sentence is unchanged; the CI job-independence criterion is checked by reading the workflow file and confirming that neither job definition declares a dependency key, which needs no push; and the version-pin criterion is checked by reading the workflow for a single version literal and, separately, by reading a completed run's package-job log for the printed resolved version, without requiring a deliberately broken push.

Fixtures are transient and never committed: a Dart file placed under `example/build/` containing a deliberate analyzer error, used to prove the build-output exclusion is load-bearing; a fake transport class defined inside the transport test; and a counter holder defined inside the example test. The demonstration that the suite reports failure is step 9's inverted assertion, with both the failing and the passing outputs pasted into the verification artifact. The two committed `analysis_options.yaml` files' pre-migrated state is checked per AC-006: each file's checksum is computed from its committed blob before any command runs, the dependency stage is run exactly once, and the checksum is computed again — the two must be equal. This is a before/after-first-run comparison, never a run-versus-run one: `AnalysisOptionsMigration` is idempotent, so a file it mutated on its first run is exactly as stable across a second run as a file that never needed mutation at all, and a run-versus-run comparison cannot tell the two apart. Comparing against the committed state is what actually demonstrates the migration found nothing to add.
