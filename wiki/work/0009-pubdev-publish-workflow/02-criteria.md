## Criteria

| ID | Criterion | How it is checked | Negative case |
|---|---|---|---|
| AC-001 | When `tools/bump_patch_version.sh` runs against a fixture root whose pubspec version is `0.1.1`, it shall exit zero and write the single line `0.1.2` to standard output with no other standard-output text. | Run the helper against a temporary copy of the fixture and compare captured standard output byte-for-byte with `0.1.2` and the exit status with zero. | Run the helper against a fixture whose version value is `0.1.1-dev.1`: it shall exit non-zero and both fixture files shall remain byte-identical to their pre-run copies. |
| AC-002 | When the helper runs against a fixture root whose pubspec version is `1.2.3`, the top-level version key of the written pubspec shall read `1.2.4`, and the first and second components shall be unchanged. | Run the helper and grep the written pubspec for a line equal to `version: 1.2.4`, asserting no line equal to `version: 1.3.0` or `version: 2.0.0` exists. | Run the helper against a fixture whose version value is `0.1` (two components): it shall exit non-zero and leave both fixture files byte-identical. |
| AC-003 | When the helper runs against a fixture root, the written CHANGELOG.md shall contain, as the first line after the single-hash Changelog title line and one blank line, a heading of exactly two hash characters, one space, the new version, one space, a hyphen, one space and the date supplied in the `RELEASE_DATE` environment variable, and that heading shall contain no square bracket. | Run the helper with `RELEASE_DATE` set to a fixed date, then assert the third line of the file equals the expected heading string and that the line contains neither `[` nor `]`. | Run the helper against a fixture whose CHANGELOG.md has no single-hash Changelog title line: it shall exit non-zero and leave both fixture files byte-identical. |
| AC-004 | When the helper runs against a fixture root, the written CHANGELOG.md shall contain, below the new heading and one blank line, exactly one bullet line equal to a hyphen, one space and the sentence `Automated patch release from main.`, and the heading that was previously top-most shall still be present below the new section with its own body unchanged. | Run the helper and compare the bullet line byte-for-byte with `- Automated patch release from main.`, then assert the previous version heading and its bullets still appear, in their original order, later in the file. | Run the helper against a fixture whose pubspec version is `0.1.1` and whose CHANGELOG.md already carries a `## 0.1.2 - 2026-01-01` heading: it shall exit non-zero and leave both fixture files byte-identical, because the two files disagree about what has been released. |
| AC-005 | When the helper is invoked in a root where pubspec.yaml is absent, it shall exit non-zero, print a message naming the missing file to standard error, create no file, and leave standard output empty. | Run the helper against an empty temporary directory and assert non-zero exit, non-empty standard error, empty standard output, and that the directory is still empty. | Run the helper against a root that holds a valid pubspec.yaml but no CHANGELOG.md: it shall exit non-zero, leave standard output empty, and leave the pubspec byte-identical, so a missing changelog cannot produce a half-applied bump. |
| AC-006 | When `tools/test_bump_patch_version.sh` runs with no network access, it shall exit zero and report each positive and negative case named in AC-001 through AC-005. | Run the test script and assert exit status zero; read the script and confirm it references no host name, no URL and no network command. | Temporarily change one fixture expectation so it disagrees with the helper output: the test script shall exit non-zero and name the failing case. |
| AC-007 | When `bash tools/check.sh` runs to completion, its output shall include a passed-stage line for the helper test stage, and the stage shall be the final numbered stage of the script. | Run the full check suite and read the output for the new stage line; read the script and confirm the stage number follows the existing sequence and uses the existing failure-reporting helper. | Make the helper test exit non-zero and re-run the suite: the suite shall stop at that stage with a non-zero exit status. |
| AC-008 | When the release workflow file is parsed as YAML, its push trigger shall list exactly one branch, `main`, and the file shall declare no pull-request trigger, no manual dispatch trigger and no tag trigger. | Parse `.github/workflows/release.yml` and assert the branch list equals the one-element list containing `main` and that the trigger mapping has no `pull_request`, `workflow_dispatch` or `tags` key. | Assert the branch list does not contain `**` or any wildcard, so a push to a feature branch matches no trigger in this file. |
| AC-009 | When the release workflow file is parsed, the bump-and-tag job shall declare a concurrency group and shall set cancellation of in-progress runs to false. | Parse the file and assert the concurrency mapping exists with a non-empty group key and that its cancel-in-progress value is the boolean false. | Assert the cancel-in-progress value is neither the boolean true nor absent, so an in-flight release is never killed by the next push. |
| AC-010 | When the release workflow file is parsed, the bump-and-tag job shall carry a job-level condition that prevents the job from running when the head commit message of the push begins with the release commit prefix `chore(release): v`, and the file shall contain no GitHub skip instruction in any commit message it writes. | Parse the file, assert the job condition tests the head commit message of the push event against that prefix, and grep the whole file for the strings `skip ci`, `ci skip`, `no ci`, `skip actions` and `actions skip`, asserting none appears. | Evaluate the guard's prefix against the message the commit step actually writes: the two shall be the same string, and a message beginning with that prefix shall be rejected by the guard while an ordinary message such as `fix: correct scope disposal` shall be accepted. |
| AC-011 | When the release workflow file is parsed, the first step of the bump-and-tag job shall be a step that reads the `RELEASE_GITHUB_TOKEN` secret and exits non-zero when the value is empty, and it shall appear before any checkout step and before any git-writing step. | Parse the file, assert the first entry of the job step list names that secret, and assert that the index of the checkout step and of every git-writing step is greater. | Extract that step's shell body, run it with the environment variable set to the empty string, and assert a non-zero exit; run it with a non-empty value and assert exit zero. |
| AC-012 | When the release workflow file is parsed, the step that runs `bash tools/check.sh` shall appear before the helper-invoking step, the commit step, the tag step and both push steps. | Parse the file and compare step indices; assert the check step exists and its index is lower than each of those. | Assert no push or tag step declares a condition that would let it run after the check step failed, for instance an always-true condition. |
| AC-013 | When the release workflow file is parsed, the commit step shall stage exactly the two paths pubspec.yaml and CHANGELOG.md, and its commit message shall begin with `chore(release): v` followed by the version the bump step produced. | Read the commit step body and assert both file paths are staged, no other path is staged, and the message begins with that prefix and interpolates the bump step's version output. | Assert the staging command is not a stage-everything invocation, so an unrelated file changed by the check suite cannot enter the release commit. |
| AC-014 | When the release workflow file is parsed, the tag step shall create an annotated tag whose name is the letter v followed by the version published as the bump step's `version` output, and the commit push step shall appear before the tag push step. | Read the tag step body and assert it requests an annotated tag with a message and a name built from that step output, then compare the indices of the two push steps. | Assert the tag step does not create a lightweight tag and that neither push step uses a force flag or deletes a ref. |
| AC-015 | When the release workflow file is parsed, both pushes shall use the `RELEASE_GITHUB_TOKEN` secret as their credential and the job shall not request write access to repository contents from the default token. | Parse the file and assert the checkout step passes that secret as its token input, and that the job or workflow permissions grant contents read. | Assert the file contains no permissions entry granting contents write, so a missing secret cannot silently fall back to the default token. |
| AC-016 | When the release workflow file is parsed, a step between the helper step and the commit step shall fail the job when a tag named after the version in the bump step's `version` output already exists locally or on the remote. | Read that step's body and assert it fetches tags and exits non-zero on an existing matching tag; assert its index lies between the helper step and the commit step. | Simulate the step's shell body in a scratch git repository that already holds a tag with that name and assert a non-zero exit. |
| AC-017 | When the publish workflow file is parsed, its only trigger shall be a push of tags matching the letter v followed by three dot-separated groups of one or more digits. | Parse `.github/workflows/publish.yml` and assert the trigger mapping has only a push key with a tags list whose single pattern is that shape. | Assert the pattern does not match the strings `main`, `v1` or `release-0.1.2`, so no branch push and no short tag starts a publish. |
| AC-018 | When the publish workflow file is parsed, its job shall call the reusable publish workflow at the path .github/workflows/publish.yml in the dart-lang setup-dart repository at reference v1, and shall grant the identity-token write permission. | Parse the file and assert the job's reusable-workflow reference string and that its permissions mapping grants id-token write and contents read. | Assert the file defines no publish command of its own and references no repository secret, so no long-lived credential can be introduced there. |
| AC-019 | When the change is complete, `.github/workflows/checks.yml` shall be byte-identical to its state before this work item. | Run a git diff limited to that path against the base commit and assert the output is empty. | Append a blank line to a scratch copy of that path and re-run the same diff command against the copy: it shall report a non-empty diff, proving the check detects a change rather than always reporting empty. |
| AC-020 | When the change is complete, the working tree shall still declare version 0.1.1 in pubspec.yaml, CHANGELOG.md shall have no section for 0.1.2, and the repository shall have no tag named v0.1.2, because the first bump belongs to the automation's first run and not to the implementation. | Grep the pubspec version line, grep the changelog for a 0.1.2 heading, and list git tags matching that name; assert the version reads 0.1.1 and the other two searches return nothing. | Run the same three searches against a temporary copy that has been given a `## 0.1.2 - 2026-01-01` heading, a bumped version line and a v0.1.2 tag in a scratch repository: each search shall report a match, proving the searches are sensitive. |
| AC-021 | When the release workflow file is parsed, the Python setup step and the Flutter setup step shall both appear before the check-suite step, and the Flutter version the release workflow pins shall equal the version `.github/workflows/checks.yml` pins. | Parse both workflow files, compare step indices in the release job, and compare the two pinned Flutter version strings for equality. | Assert the release job declares no step that runs `bash tools/check.sh` before those setup steps, and assert the comparison fails when the checks workflow's pinned version string is substituted with a different value. |
| AC-022 | When either new workflow file is read, it shall carry an English comment naming its operator prerequisite: the release file the `RELEASE_GITHUB_TOKEN` secret and the branch-protection allowance on main, the publish file the pub.dev automated-publishing setting with the tag pattern `v{{version}}` for repository `ortal83cohen/flutter_webmcp`. | Grep each file for a comment line naming those items and assert one is present in each. | Assert the grep pattern returns nothing when run against `.github/workflows/checks.yml`, so the check is matching the new comments rather than any comment in any workflow. |

## Non-functional criteria

| ID | Criterion | How it is checked | Negative case |
|---|---|---|---|
| AC-023 | When every file added or changed by this work item is searched for credential material, the only credential reference found shall be the named secret lookup for `RELEASE_GITHUB_TOKEN`; no pub.dev password, no credentials JSON path and no access token literal shall appear. | Grep the added and changed files for pub credentials vocabulary and for long token-shaped literals; assert the only match is the secret reference. | Plant a credentials-file path and a token-shaped literal in a scratch copy of one added file and re-run the same grep: it shall match both, proving the pattern set detects planted credential material. |
| AC-024 | When the helper rejects an input, neither pubspec.yaml nor CHANGELOG.md in the target root shall differ by a single byte from its pre-run content. | For each negative fixture, checksum both files before and after the run and compare. | Re-run the same comparison against a copy that has been modified by one byte after checksumming: the comparison shall report a difference, proving it is not passing vacuously. |
| AC-025 | When the helper and its test run, neither shall open a network connection, so the check suite stays runnable offline. | Read both scripts and confirm no URL, host name or network command; run the test suite with no network reachable and assert exit status zero. | Add a temporary case that resolves a host name and run the suite offline: that case shall fail, proving the suite would notice a network dependency. |

## Explicitly not required

- Interpreting commit messages to choose a minor or major bump. Every automated release is a patch bump.
- Creating a GitHub Release, release notes or a discussion for the tag.
- Publishing from a pull request, from a feature branch or from a manual dispatch.
- Proving that automated publishing is enabled on pub.dev, that the `RELEASE_GITHUB_TOKEN` secret exists, or that branch protection on main permits the push. These are operator prerequisites recorded as human gates; the release job fails closed on the missing secret and the other two are proved by the first real release attempt.
- Pinning the SDK the delegated Dart publish workflow installs. That workflow owns its own toolchain and the research artifact records its default as unpinned.
- Retracting or unpublishing a version, and any tooling around the retraction window described in this work item's research file on automated publishing.
- Synchronising the package version into any wiki document.
- An end-to-end run that actually publishes 0.1.2 to pub.dev during the verify phase. A published version is permanent, so verification is static analysis of the workflow files plus offline tests of the helper.
