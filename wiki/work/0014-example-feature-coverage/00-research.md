# Research: Example app covers every webmcp_flutter feature and is verified in Chrome

## Question

Does `example/` demonstrate every public feature of `webmcp_flutter` (including the generated-domain-actions path via `webmcp_flutter_generator`), and can that example be run and verified in an external Chrome browser?

## Answer

`example/` today exercises only the happy path: manual tool registration through `WebMcp.instance`/`WebMcpScreen`/`WebMcpAction`, one automatic `WebMcpPage`, one root `WebMcpNavigatorAdapter`, and two fields of the native publisher's status. Roughly a third of the package's public surface — tool sources, the exception family, custom transports, registry observers, tool annotations/input schemas, and page-policy/limits customization — is never exercised. Generated domain actions (`webmcp_flutter_generator`/`webmcp_flutter_annotations`) are not referenced by the top-level example at all, though a working reference pattern already exists in `packages/webmcp_flutter_generator/example/`.

The example can be run in an external Chrome via `flutter run -d chrome` (the README's own documented recipe) and its UI-level behavior — tool registration lists, counter increment, page navigation, native-publisher status text — can be verified visually in the browser. The native Chrome `document.modelContext` surface itself is Chrome-experimental and its currency is only partially settled here: this repo's spike (`wiki/work/0008-automatic-page-agent/05-transport-spike.md:98-113`) recorded one working flag set (`--enable-features=WebMCP,WebMCPTesting --enable-experimental-web-platform-features`) over an HTTPS/COOP-COEP-isolated origin and one failed partial-flag probe — it never tested a plain HTTP dev server, so whether `flutter run -d chrome`'s default server would expose `document.modelContext` (with or without flags) is `[UNRESOLVED]`, not a settled negative. Chrome's own public docs (developer.chrome.com/docs/ai/webmcp, checked 2026-09-15) describe a `chrome://flags/#enable-webmcp-testing` local-dev path and an origin trial running Chrome 149–156, with the stated security requirement being an origin-isolated document (not a certificate/COOP-COEP requirement) — a materially cheaper option this research did not originally price. Either way, "verify in Chrome" for this work item targets the app's own local `WebMcp.instance` registry and on-screen behavior; the example's on-screen `Native publisher: <status>` text is recorded as observed, whatever support level a normal Chrome install reports, and that is the correct, verifiable outcome — no attempt is made to force `conformanceUsable`.

## Findings

### Coverage gaps in the current example (ranked)

1. `WebMcpToolSource` / `WebMcp.registerSource` / `WebMcpScope.addSource` / `WebMcpPage.sources` — entirely absent; this is the primary extensibility seam and the shape generated adapters use.
2. `WebMcpException` family (`WebMcpInvalidToolNameException`, `WebMcpDuplicateToolException`, `WebMcpToolNotFoundException`, `WebMcpScopeMissingException`) — never triggered or caught anywhere.
3. Custom `WebMcpTransport` and `WebMcp.reset(transport)` — never demonstrated; only the platform default is ever active.
4. `WebMcpPagePolicy` customization, especially `setText`/`allowLongPress` — the example has no text field or long-pressable/scrollable widget, so most of `.page.act` is unreachable.
5. `WebMcp.addRegistryObserver` / `WebMcpRegistryObserver` / `WebMcpRegistryResetObserver` — never shown as a consumer-usable pattern.
6. `WebMcpToolAnnotations` and non-default `WebMcpTool.inputSchema` — every tool uses defaults.
7. `WebMcpAppSession` diagnostics and direct invocation of `.app.observe`/`.page.read`/`.page.act` — only exercised indirectly through manual UI taps, never through an automated/explicit call.
8. Full `WebMcpNativePublisherStatus`/`WebMcpNativeCapabilities` diagnostics — only `status.support.name` and `capabilities.positiveWait` are shown; `publishedToolCount`, `skippedToolCount`, `reasonCodes`, `toDiagnosticMap()`, etc. are not.
9. `WebMcpViewProvider`/`WebMcpPageLimits` custom injection — lower priority, defaults are reasonable for a pilot.
10. Nested/parallel `WebMcpNavigatorAdapter` usage (`parentNavigatorId`, `persistentParallelBranch`, `selectedBranch`) — lower priority given the single-Navigator structure.

Full feature-by-feature table with file:line evidence: `wiki/work/0014-example-feature-coverage/research/api-surface-coverage.md`.

`lib/src/transport/native_publisher_boundary*.dart` is internal (never exported from `lib/webmcp_flutter.dart`) and is therefore excluded — it cannot be a "missing example coverage" item since a consumer cannot import it.

### Generated domain actions (webmcp_flutter_generator)

The top-level `example/` has zero references to `webmcp_flutter_annotations`, `webmcp_flutter_generator`, or `@WebMcpDomainAction` (repo-wide grep, no matches). `webmcp_flutter_annotations` is a single metadata-only annotation class. `webmcp_flutter_generator` is a `build_runner` `LibraryBuilder` that emits a `.webmcp.g.dart` adapter (implementing `WebMcpToolSource`) for annotated public instance methods only, wrapping a consumer-supplied live instance — it never constructs the service or grants authorization (`wiki/product/webmcp-contract.md:90-96`). A working, tested reference already exists at `packages/webmcp_flutter_generator/example/` (fixture service + `live_instance_test.dart`), so the pattern does not need to be invented.

Adding this to the top-level example requires: a new runtime dependency (`webmcp_flutter_annotations`), new dev_dependencies (`build_runner`, `webmcp_flutter_generator`), and a `build_runner build` step to produce a checked-in `.webmcp.g.dart` file. Full detail: `wiki/work/0014-example-feature-coverage/research/generator-coverage.md`.

### Running and verifying in Chrome

- Build/run: `cd example && flutter pub get && flutter run -d chrome` (`README.md:606-612`). `tools/check.sh` uses `flutter build web` (static artifact only, no serve) as its CI check. Port is ephemeral, printed by the CLI at run time — not fixed anywhere in the repo.
- The native publisher targets `document.modelContext` (not any `window.*` path) — `lib/src/transport/native_publisher_boundary_web.dart:26-31`. It calls `.registerTool({name, description, inputSchema, annotations, execute}, {signal})`.
- This repo's own spike (`wiki/work/0008-automatic-page-agent/05-transport-spike.md:98-113`) shows `document.modelContext` only appeared in Chrome 152 launched with `--enable-features=WebMCP,WebMCPTesting --enable-experimental-web-platform-features` against an HTTPS, COOP/COEP-isolated origin; a partial flag set failed. A plain `flutter run -d chrome` HTTP dev server was never tested against this and is a real, open gap (`[UNRESOLVED]` whether it would work even with the right flags).
- The example's own UI already surfaces verification signals without any console work: a `Text(names)` widget lists every currently-registered tool name, and `Native publisher: ${status.support.name}` / `Positive observe wait: ${capabilities.positiveWait}` show native-publication status directly on screen.
- Registered tool names at runtime: `example.counter.read`, `example.counter.increment` (always), `example.screen.describe`, `example.screen.increment` (only while `ExampleScreen` is mounted — they disappear on the details page and reappear on return).
- Manual console invocation via `document.modelContext.executeTool(...)` is explicitly disclaimed by the product contract as native-agent proof (`wiki/product/webmcp-contract.md:141-144`) — any browser verification in this work item should be framed as confirming the app's own local registry/UI behavior and native-publisher status reporting, not as proof of real AI-agent tool use.

Full detail: `wiki/work/0014-example-feature-coverage/research/browser-verification.md`.

### Corrections from validation round 1 (research-review-01)

The following corrects the original draft against verified re-reads of `lib/src/page/webmcp_page.dart`, `lib/src/page/webmcp_app_session.dart`, and `lib/src/transport/webmcp_native_publisher.dart`:

- **Full runtime tool-name enumeration (fixes F-001).** The originally listed four tool names were incomplete. Once `main.dart` calls `session.attach(appId: 'example')`, `WebMcpAppSession.attach` also registers `example.app.observe` (`lib/src/page/webmcp_app_session.dart:175-182`). Once a `WebMcpPage` becomes eligible (see next point), it registers `<pageId>.page.read` and `<pageId>.page.act` (`lib/src/page/webmcp_page.dart:575-590`) — for the current example, `example.home.page.read`/`.act` while the home screen is the active page, and `example.details.page.read`/`.act` while the details route is on top. The home screen's on-screen tool list is unfiltered `WebMcp.instance.tools` (`example_screen.dart:45-47`), so all of these appear in it. Any acceptance criterion enumerating "the" registered tool list must include these session/page endpoints, not just the manually-registered and screen/action tools.

- **Page-endpoint eligibility precondition (fixes F-002/F-004, plan F-001/F-004).** `<pageId>.page.read`/`.act` and a page's `sources` tools register only after `_captureNow` sets `_eligible` true (`lib/src/page/webmcp_page.dart:352`), which requires: a non-null `WebMcpAppSession` captured at `initState` (`:104,113-117,274-277`); exactly one view from the view provider (`:281-285`); and `_activityIsProved()`, which needs a non-null `ModalRoute.of(context)` whose navigator is owned by exactly one settled `WebMcpNavigatorAdapter` (`:341-347`; `webmcp_app_session.dart:114-139`), evaluated in a post-frame callback. This is a real harness requirement, not an incidental detail — the library's own tests build a `WebMcpAppSession`, `attach` it, construct a `WebMcpNavigatorAdapter`, wrap the widget in a `MaterialApp` with that adapter as a `navigatorObserver`, then pump multiple frames before any page tool is registered (`test/page/webmcp_page_test.dart:1031-1073`). Any plan step that exercises `.page.read`/`.act`/page-`sources` in a widget test must specify this exact harness and name which task owns building it, since more than one task needs it.

- **Page read node wire shape has no semantics-identifier field (fixes plan F-001/F-002/F-003).** The serialized node in a `.page.read` response carries `handle`, `role`, `label`, `hint`, `value`, `states`, `actions`, optional `bounds`, optional `parentHandle` (`lib/src/page/webmcp_page.dart:521-548,891-901`) — there is no `identifier`/semantics-identifier field in the wire. The Flutter `Semantics.identifier` value is retained only internally, on `_CapturedNode.semanticsIdentifier` (`:452`), for act-time revalidation (`:1037`); it is never serialized to a caller. Any plan that has a probe or a test "target the node whose semantics identifier matches X" is targeting a field that does not exist in the response. The only caller-visible discriminators are `role`, `label`, `hint`, `value`, and `states`/`actions`. A workable design gives each demonstrated widget a distinct, human-readable `label` (via a `Semantics(label: ...)` wrapper or the widget's own accessible name) and has the probe/tests match on `label`, not on the internal semantics identifier.

- **`.page.act` required arguments and request-identifier/retry semantics (fixes plan F-021).** The act endpoint requires `pageId`, `mountToken`, `revision`, `handle`, `action`, `requestId`, and `arguments` (`lib/src/page/webmcp_page.dart:1234-1246`, enforced `:921-941`). `requestId` must be at least 1 and strictly greater than the highest previously seen value for that page, or the call returns `duplicateRequest` unless the request's fingerprint is byte-identical to the one already seen for that id (`:988,1004-1010`). A retry after a `staleSnapshot` failure necessarily carries a different `revision` (hence a different fingerprint) than the first attempt, so a retry that reuses the same `requestId` gets `duplicateRequest`, not a fresh attempt — any retry design must increment `requestId` on each attempt.

- **Diagnostic map overlap (fixes plan F-013 / research F-006).** `WebMcpNativePublisherStatus.toDiagnosticMap()` already spreads `WebMcpNativeCapabilities.toDiagnosticMap()`'s four keys into itself (`lib/src/transport/webmcp_native_publisher.dart:65-74`) — the capability keys are a strict subset of the publisher keys, not a disjoint set. A "show every diagnostic key" design must render the publisher map once (which already contains the capability keys) rather than both maps separately, to avoid duplicate rows. `reasonCodes` is an empty list in the normal `localOnly` case (`:251-253`) — a design that requires "every row shows a non-empty value" must treat an empty-list rendering (e.g. the literal text "none") as satisfying non-emptiness, or exclude that key from the non-empty-value requirement.

- **Generated-adapter `dependency_overrides` rationale (fixes research F-008).** `packages/webmcp_flutter_generator/pubspec.yaml:14-15,23-25` depends on the *hosted* `webmcp_flutter_annotations: ^0.1.0` and itself overrides that to the in-repo path `../webmcp_flutter_annotations`. Because Dart/Flutter dependency overrides are not transitive across packages, a consumer of the generator (such as `example/`) that also wants the in-repo, unpublished `webmcp_flutter_annotations` must declare its own `dependency_overrides` entry — this is exactly why `packages/webmcp_flutter_generator/example/pubspec.yaml:24-26` carries the same override. Without it, `flutter pub get` in `example/` would either fail to resolve or silently pull the hosted `webmcp_flutter_annotations` package instead of the in-repo one, which could diverge in API shape from what the generator emits against.

- **Additional exported public declarations omitted from the original coverage table (fixes research F-007, partially).** `lib/src/page/page.dart:4-13` also exports `WebMcpEvidenceKind` (returned by `.name` in act receipts, `webmcp_page.dart:1095`), `webMcpPageProtocolVersion`, and `webMcpMaxSafeInteger`. These are additional, lower-priority candidates for demonstration; the plan should note their existence but is not required to build dedicated demonstrations for constants/enums whose only use is being echoed back in an existing response shape already exercised by other criteria.

- **AC-021 must not reclassify supported-but-out-of-scope features as contract prohibitions (fixes research F-009).** Nested/parallel `WebMcpNavigatorAdapter` usage, `WebMcpViewProvider` customization, and `WebMcpPageLimits` customization are real, working features that this work item simply chooses not to demonstrate (lowest-priority gaps, ranked #9–#10 above) — they are not on `wiki/product/webmcp-contract.md`'s "Deliberate omissions" list (`:146-153`). Criteria must keep these in a distinct "chosen not to demonstrate" bucket, separate from actual deliberate-omissions checks, so that a criterion never asserts the contract forbids something it does not forbid.

## Constraints discovered

- Everything in `wiki/product/webmcp-contract.md`'s "Deliberate omissions" section (multi-view, positive observation waits, generated route wrapping/service proxies/state adapters/data providers, back-gesture support, in-flight callback termination, deep schema immutability, transactional source registration/rollback, automatic custom-transport cleanup, non-web support) must **not** be treated as a coverage gap to fix.
- Any generated-domain-action demo must construct its own service instance and own the `WebMcpScope`/cleanup explicitly — generated adapters never construct services or grant authorization (`wiki/product/webmcp-contract.md:90-96`).
- Adding `webmcp_flutter_annotations`/`webmcp_flutter_generator`/`build_runner` to `example/pubspec.yaml` is a new-dependency change — this alone rules out `/quick-change` for that slice of the work, consistent with routing the whole work item through `/feature` (already decided at Step 0).
- `document.modelContext` conformance cannot be reliably demonstrated over the plain `flutter run -d chrome` HTTP dev server based on current in-repo evidence; browser verification in this work item should target the app's own local/UI-visible behavior (tool list, counter, navigation, on-screen native-publisher status), not forced native-surface conformance.
- No fixed Flutter web port is configured anywhere in this repo; the actual served URL must be read from the `flutter run -d chrome` CLI output when it is actually run.
