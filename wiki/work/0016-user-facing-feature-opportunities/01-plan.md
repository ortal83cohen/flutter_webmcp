# Plan: Feature opportunities for application authors using webmcp_flutter

## Goal

After this change, an application author who publishes a tool through the native publisher can read the browser execution signal and stop their own in-flight work, can set a display title, a debugging hint, and an origin list, and can hear tool-start and tool-cancel events. A manual tool can decode a declared input shape before the author callback runs, can throw a structured failure the browser agent receives as an allowlisted error object, and can install a logger that records tool names and event kinds. On a non-web host, local registration and local invocation still run, and native publication completes without throwing. The library still does not terminate or replay a handler.

## Approach

The execution signal stays an author-owned cancellation handle. `BrowserWebMcpNativeBoundary` in `lib/src/transport/native_publisher_boundary_web.dart` today registers an `execute` function that accepts only the input value and then calls `_executeSafely` with `cancelledBeforeDispatch` set to false. That callback will also read the second argument, the browser options object, and take its `signal` when that property is present. The boundary adapts that browser signal into a new Dart value, `WebMcpExecutionSignal`, defined in `lib/src/webmcp_tool.dart`. The adapter exposes whether the signal has aborted and lets the author add and remove an abort listener. It does not abort the signal itself, does not complete the handler future, and does not call the handler a second time. When the second argument or its signal is missing, the adapted value is null and the handler still runs. `cancelledBeforeDispatch` remains the only path that skips the handler, and it stays a separate flag on `WebMcpNativeInvocationContext` in `lib/src/transport/native_publisher_boundary.dart`.

The existing one-argument `WebMcpToolHandler` stays the default. `WebMcpTool` gains an optional `callHandler`. When `callHandler` is set, `WebMcp.invokeTool` in `lib/src/webmcp.dart` and `WebMcpNativePublisher._invoke` in `lib/src/transport/webmcp_native_publisher.dart` call it with a `WebMcpToolCall` that carries the arguments and the execution signal. Local invocation and every non-web call pass a null signal. When `callHandler` is null, the existing `handler` runs exactly as it does now and never receives a signal. Supplying both callbacks is rejected at construction. The page source wrapper in `lib/src/page/webmcp_page.dart` uses that same choice: a tool with `callHandler` is invoked through that callback with a null execution signal, and a tool with only `handler` is invoked through `handler`. Page dispatch does not read a browser signal. `WebMcpAction` in `lib/src/widgets/webmcp_action.dart` keeps exactly one author callback. `onInvoke` stays the one-argument path and is stored only as `handler`. A new optional `onCall` is stored only as `callHandler`. Exactly one of those two widget callbacks is required, and the widget never constructs a tool with both. Those descriptor values, like name, description, and input schema, stay fixed at the first mount.

Display metadata is optional and is omitted from the browser registration object unless the author set it. `WebMcpTool` gains an optional `title`. `WebMcpToolAnnotations` gains an optional `debugging` boolean. `WebMcpTool` gains an optional `exposedTo` list of origin strings, copied into an unmodifiable list at construction. `BrowserWebMcpNativeBoundary.registerTool` adds `title` only when title is non-null, adds `debugging` inside the annotations object only when debugging is non-null, and adds `exposedTo` only when the list is non-null. A null debugging value is left out of the registration object rather than sent as false. The library does not check whether a user agent shows the title, and it does not check whether an agent filters a debugging hint. Origin strings are forwarded as the author supplied them. An origin the browser rejects follows the existing registration-failure path and is recorded as `registrationFailed`.

Tool activity is notification only. `WebMcpNativeBoundary` gains a way for the publisher to subscribe to and unsubscribe from browser tool activity. The web boundary listens on `document.modelContext` for `toolactivated` and `toolcancel`, reads `toolName`, and reports a `WebMcpNativeToolActivity` whose kind is started or cancelled. `WebMcpNativePublisher` forwards those events to listeners added with `addToolActivityListener`, which returns a cancellable subscription. Listening begins when `attach` succeeds in detecting a model context and ends on `detach`. A missing event target does not fail publication; the publisher records `browserUnavailable` for activity and still mirrors tools. A start or cancel event does not call, abort, or replay a handler. The registration abort signal remains the existing cleanup path and still does not abort an execution signal.

Typed decode is a declared field list, not a check of the free-form schema map. A new `lib/src/webmcp_typed_input.dart`, exported from `lib/webmcp_flutter.dart`, defines `WebMcpInputField` and `webMcpDecodeArguments`. A field names a key and a shape: string, boolean, safe integer, finite double, enumeration name, list, or string-keyed map, including nullable forms and nested lists and maps. Safe integers use the same inclusive bounds the generator already uses, from -9007199254740991 through 9007199254740991. An integer field rejects a double. An enumeration field accepts only the names the author listed. Unknown keys, missing required keys, and values of the wrong shape throw `WebMcpInvalidArgumentsException` before the author callback. `WebMcpTool.withDecodedArguments` builds a tool whose `callHandler` decodes first and then calls the author callback with the decoded map. It does not also set `handler`. `registerTool` still stores `inputSchema` as a descriptive shallow copy and does not walk it as JSON Schema.

Structured agent errors stay on the browser boundary. A new `WebMcpToolException` in `lib/src/webmcp_exceptions.dart` carries a code, a retryable flag, and an optional details map. `WebMcp.invokeTool` lets that exception propagate to the local caller, unchanged, as it does for every other handler exception. `WebMcpNativePublisher._invoke` catches `WebMcpToolException` and returns the existing safe failure JSON object, with the author code and the retryable flag, and with details only after they pass the current depth and encoded-size checks in `_normalizeJson` and `_enforceEncodedSize`. The agent object does not include the exception message, a stack, the arguments, or the schema. If the code is empty, longer than 64 characters, or outside ASCII letters, digits, underscores, hyphens, and periods, or if details fail those bounds, the publisher returns the existing `handlerFailed` object and does not include the author payload. Every other thrown object still becomes `handlerFailed`.

The logger is a process-wide hook that cannot see payloads. `WebMcp.logHook` is a static function, null by default, receiving a `WebMcpLogRecord` with a kind and a tool name, and an optional reason code. Kinds are registered, unregistered, invoked, invocationFailed, and nativeActivity. `registerTool`, `unregisterTool`, `invokeTool`, and the publisher write those records. The record type has no field for arguments, results, schemas, or stacks. An exception thrown by the hook is swallowed and does not change registration, invocation, or publication. `reset` does not clear the hook.

Non-web registration is local and native publication is a no-op. `NoopWebMcpNativeBoundary.registerTool` in `lib/src/transport/native_publisher_boundary_noop.dart` returns a registration whose `abort` does nothing, instead of throwing `browserUnavailable`. `WebMcpNativePublisher.attach` keeps its current undetected path: it records `browserUnavailable`, publishes nothing, and completes. `registerTool` and `invokeTool` keep working on the local registry. `pubspec.yaml` lists android, ios, linux, macos, windows, and web so a non-web application can depend on the package. That listing is not support for automatic pages, browser agents, or more than one Flutter view.

## Why this approach

The user decision in `STATE.yaml` selects the three scopes and rejects deferral. `00-research.md` records that demand-signals.md chose deferral; that choice is not followed. browser-contract-gaps.md chose exposing the execution signal and rejected both a second `document.modelContext` registration beside the publisher and keeping the signal omitted. Those two rejections stand: while `WebMcpNativePublisher` owns `execute`, application code cannot see the signal, and omitting it leaves the author unable to stop their own work.

Library-initiated termination stays rejected. The product contract lists in-flight callback termination under deliberate omissions, and the draft's registration-abort path leaves the execution signal alone. This plan forwards the signal and leaves the handler running until the author returns. Replaying the handler after a cancel event is the same forbidden termination policy and is not done.

An ambient zone that exposes the current signal was rejected. A zone is easy to lose across an asynchronous gap, and the call object makes the signal a parameter the author asked for. Changing `WebMcpToolHandler` to require a second argument was rejected because every existing one-argument handler would stop compiling. Sending `debugging: false` whenever the author omitted the hint was rejected because `00-research.md` leaves unresolved whether omission differs from false. Validating the free-form `inputSchema` map as JSON Schema was rejected by the user decision; the generator's typed shapes already exist, and the manual decoder reuses those shapes without reading the schema map. Copying the comparable package's success result types was rejected because the chosen scope is structured errors, and local results already pass through unchanged.

Absorbing the remaining author glue was rejected by the user decision and by current-user-jobs.md as a description of current behavior. This plan does not add runtime JSON Schema validation of free-form maps, generated route wrapping, generalized service proxies, positive observation waits, transactional registration, automatic transport cleanup, or multiple-Flutter-view support. A Wasm lifecycle fix and a pub.dev publish were not chosen and stay out.

## Steps

1. Add `WebMcpExecutionSignal`, `WebMcpToolCall`, optional `callHandler`, optional `title`, optional `exposedTo`, and optional `debugging` on `WebMcpToolAnnotations`, with construction rules, in `lib/src/webmcp_tool.dart`. Thread the optional descriptor fields through `WebMcpAction`. Add optional `onCall` beside the existing `onInvoke`, require exactly one of them, and store only the matching tool callback. Do not change the first-mount descriptor rule. Existing one-argument handlers still construct and run.

2. Teach `WebMcp.invokeTool` and the page source wrapper in `lib/src/page/webmcp_page.dart` to prefer `callHandler` and to pass a null execution signal. A call-handler-only tool remains invocable from that wrapper. Add `WebMcpToolException`, `WebMcpInvalidArgumentsException`, `WebMcpLogRecord`, and `WebMcp.logHook` in the registry and exception files. Swallow hook failures. Leave local exception propagation unchanged.

3. Add `lib/src/webmcp_typed_input.dart` and `WebMcpTool.withDecodedArguments`. Decode the declared fields before the author callback. Export the new library members from `lib/webmcp_flutter.dart`.

4. Extend `WebMcpNativeInvocationContext` so the publisher can carry the adapted execution signal into `_invoke` without treating abort as a reason to skip, complete, or replay the handler. Keep the `cancelledBeforeDispatch` short-circuit. Map `WebMcpToolException` to the safe failure object under the code and details rules above. Emit logger records that contain only kind, tool name, and an optional reason code.

5. Change `BrowserWebMcpNativeBoundary` so `execute` reads the second argument's signal, adapts it, and passes it through. Add title, debugging, and exposedTo to the registration object only when set. Subscribe to `toolactivated` and `toolcancel` and report tool name and kind. Change `NoopWebMcpNativeBoundary.registerTool` to return a no-op registration. Add `addToolActivityListener` on `WebMcpNativePublisher`, started from `attach` and stopped from `detach`. List the non-web Flutter platforms in `pubspec.yaml`.

6. Extend `test/native_publisher_test.dart`, the registry tests, the page-dispatch tests, and the widget tests so each acceptance criterion has a passing check and the negative case named in `02-criteria.md`. The signal test uses a fake boundary and a fake signal. It does not launch Chrome and does not assert that a browser aborted the signal. The page test covers a call-handler-only tool and a handler-only tool. The widget test covers `onCall` alone, `onInvoke` alone, and both together.

## Interfaces and shared decisions

`WebMcpTool.callHandler` is optional. It is a function that receives one `WebMcpToolCall` and returns the same future-or-value the existing handler returns. `WebMcpToolCall.arguments` is the decoded or raw argument map. `WebMcpToolCall.executionSignal` is a `WebMcpExecutionSignal` or null. The signal type exposes `aborted` and listener add and remove methods. It has no method that asks the library to cancel the handler. A tool constructed with both `handler` and `callHandler` throws `ArgumentError` before registration. A tool constructed with neither also throws `ArgumentError`.

`title` null means the registration object has no title member. `debugging` null means the annotations object has no debugging member. `debugging` true or false is copied into that member. `exposedTo` null means the registration object has no exposedTo member. A non-null list, including an empty list, is copied unmodifiable and sent as that list. Entries are strings. The library does not parse them as URLs. `WebMcpAction.onInvoke` maps only to `handler`. `WebMcpAction.onCall` maps only to `callHandler`. The widget requires exactly one of them and throws `ArgumentError` before registration when both are set or when neither is set. It accepts the same optional title, annotations, and exposedTo, and still treats the child as an unchanged render.

`WebMcpInputField` names one key, one shape, whether it is required, and, for an enumeration, the allowed names. Nested list and map fields name a child field. `webMcpDecodeArguments` returns a new map containing only declared keys. `WebMcpTool.withDecodedArguments` requires a call handler that receives the decoded map through `WebMcpToolCall`. Decode failure throws `WebMcpInvalidArgumentsException` and does not call that handler. The registry does not read `inputSchema` during decode.

`WebMcpToolException` is the only handler exception the publisher turns into an author-coded agent error. The JSON object keeps the current shape: `ok` false, and `error` with `code` and `retryable`. Details, when accepted, are an additional `details` object on `error`. Local `invokeTool` does not catch it. `WebMcpInvalidArgumentsException` is a `WebMcpToolException` whose code is `invalidArguments` and whose retryable flag is false, with no details.

`WebMcp.logHook` defaults to null. `reset` leaves it in place. Records use the kinds registered, unregistered, invoked, invocationFailed, and nativeActivity. `WebMcpNativeToolActivity` carries kind started or cancelled, plus the tool name string from the event. Listeners added after `detach` receive nothing until a later `attach`. Listener exceptions are swallowed.

Non-web `attach` still reports the browser unavailable and owns zero native registrations. The no-op registration's `abort` may be called any number of times.

## Risks

| Risk | Likelihood | Impact | Mitigation | Trigger that means it happened |
|---|---|---|---|---|
| A browser that ignores an unknown registration member rejects the whole tool. | Medium | The tool stays local and is skipped with `registrationFailed`. | Send title, debugging, and exposedTo only when the author set them, and keep the existing skip path. | A tool that registered before these members were set is skipped only after the author sets one of them. |
| Authors treat a forwarded signal as proof that Chrome aborts in-flight work. | Medium | Handlers wait for an abort that this work item does not claim. | Tests drive a fake signal. The plan and the criteria forbid a Chrome-abort claim. The diagnostic flag `invocationCancellationAfterCallbackStart` stays false. | A test or a document asserts that a current Chrome build aborted the signal after the callback started. |
| A logger or a structured error records arguments or a stack. | Low | Agent or log output leaks invocation data. | The log record type has no payload fields. The agent object omits message and stack, and details that fail the existing bounds become `handlerFailed`. | A test observes argument text, schema text, or a stack in a log record or in the agent failure object. |
| Widening `pubspec.yaml` platforms is read as non-web page support. | Medium | Authors expect automatic pages on mobile or desktop. | The no-op boundary only changes native registration. Page eligibility stays one Flutter view on web. The document phase narrows the omission sentence and leaves page support omitted. | A non-web test expects a page read or a native tool list to succeed. |

## Rollback

This work item does not publish to pub.dev. Before publication, rollback is reverting the change set: the new optional fields and the call handler disappear, `execute` returns to one argument, the noop boundary throws again on `registerTool`, and the platforms list returns to web only. Existing one-argument handlers keep compiling during the change, so the revert does not require a data migration. After a later release publishes the new public members, removing them would be a breaking change. That later release is outside this work item. Nothing in this change writes durable user data, so there is no irreversible data step.

## Out of scope

Library termination or replay of an in-flight handler stays omitted. The plan does not claim that a current Chrome build aborts the execution signal after the callback starts. It does not claim that omitting debugging differs from false, and it does not claim that agents filter the hint. It does not claim that any user-agent surface shows title. Declarative HTML forms stay out. Wasm automatic-page lifecycle stays out. Publishing `webmcp_flutter`, `webmcp_flutter_annotations`, or `webmcp_flutter_generator` stays out. The plan does not claim that the score-window downloads are application authors.

Runtime JSON Schema validation of free-form maps, generated route wrapping, generalized service proxies, positive observation waits, transactional registration, automatic transport cleanup, and multiple-Flutter-view support stay out. Authorization inside handlers stays with the author. `getTools`, `executeTool`, `fromOrigins`, permissions policy, and `outputSchema` stay out. `toolchange` remains not application-state delivery. The document phase, not this implementation, edits `wiki/product/webmcp-contract.md` and the README. That edit keeps in-flight callback termination in the omission list, and it states that non-web hosts can register and invoke locally while native publication reports the browser unavailable. It does not pick a Wasm automatic-page statement.

## Verification approach

`bash tools/check.sh` is the full gate. Focused tests are `flutter test test/native_publisher_test.dart` and the registry test that covers decode, logger, and local exceptions. A fake boundary supplies the second callback argument and a signal whose aborted flag the test flips after the handler has started; the assertion is that the handler future is still pending until the handler returns, and that the handler ran once. A second test sets `cancelledBeforeDispatch` and asserts the handler was not called. Descriptor tests read the registration object the fake boundary captured and assert members are absent when unset and equal to the author value when set. Activity tests emit fake `toolactivated` and `toolcancel` events and assert a listener observed the tool name and that the in-flight handler was not completed by the cancel event. Decode tests pass one valid shape and one unknown field, one integer outside the safe bounds, and one free-form schema map that is never read. Exception tests compare the encoded agent object for `WebMcpToolException` with the object for a generic throw, and assert that local `invokeTool` still throws. Logger tests assert the record's tool name and kind and assert that a throwing hook still leaves the tool registered. The non-web test constructs `NoopWebMcpNativeBoundary`, registers, aborts, and attaches a publisher, and asserts no throw and a zero published count. `python3 tools/lint_wiki.py` runs before the plan phase is reported done.
