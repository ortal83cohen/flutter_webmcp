# Plan: Flutter WebMCP package skeleton

## Scope note and unresolved-item check

This plan covers the **project skeleton only**, as defined by the `bootstrap-product` skill: a working toolchain, one runnable entry point, a test suite proven to report failure, a formatter and linter, a single check command, and CI. It does not cover the full WebMCP browser integration.

The research artifact `00-research.md` lists eight `[UNRESOLVED]` items (two of the original seven were resolved during validation and replaced with two newly surfaced ones — see the research artifact's own corrections note). None of them blocks this plan, and each is handled rather than silently dropped:

- The `chrome://flags` question, the `outputSchema` mechanism, and the exact `pana` rule text affect only work explicitly placed out of scope below.
- Per-screen tool shadowing is decided here, not deferred: the skeleton has one flat tool namespace, no shadowing.
- The line-by-line capability diff against `KickNext/flutter_webmcp` has still not been performed. It is marked `[UNVERIFIED]` and is a prerequisite for publishing, which is out of scope. Differentiation is nonetheless decided concretely in this plan rather than left open.
- Whether `dart-lang/web`'s issue tracker already has an open proposal to add `modelContext` to the generated `Document` type: not checked before implementation starts a step 7 file the plan already commits to writing as a temporary `extension`-based workaround regardless of the answer; if such a proposal exists it only shortens a future removal, it does not change what step 7 writes now.
- Whether the WebMCP-org/MCP-B toolkit is still the maintained reference implementation, and whether `intentcall_platform` is a third relevant prior-art package: neither affects this skeleton's design, since the package does not depend on or compete against either directly; both are recorded as follow-ups for the publishing work item alongside the capability diff.

## Goal

After this work item, the repository contains a resolvable, analyzable, testable Dart/Flutter package under a decided name, plus a Flutter web example application that starts in Chrome, registers one tool through the package's public registry API, and reports on screen whether the browser exposes a WebMCP model context — behaving identically without error when it does not. A single command runs format checking, static analysis, the package tests, the example tests and the wiki linter, exits zero on a clean checkout, and exits non-zero when any one stage is broken. GitHub Actions runs that same command on every push and pull request alongside the existing wiki lint job. The suite has been demonstrated to report a failure, not merely assumed capable of it.

## Approach

The package is a single non-plugin Flutter package rooted at the repository root: `pubspec.yaml`, `analysis_options.yaml`, `README.md`, `CHANGELOG.md`, `LICENSE` and `lib/` sit beside the existing `wiki/`, `tools/`, `.github/` and `.claude/` directories. This keeps the `pana`-visible layout that the research identified — `lib/`, `example/`, `test/`, the four metadata files — at one path, with no monorepo indirection, matching the single-package intent. The example lives in `example/` as its own Flutter application package with a path dependency on the root package, so it can be run with `flutter run -d chrome` and built with `flutter build web`.

The public surface is exported from exactly one library file, and every implementation file lives under `lib/src/`. The centre of the design is a static facade, `WebMcp`, holding an in-memory ordered registry of tool definitions. Registration validates the tool name against the character rule the WebMCP IDL specifies, stores the definition, and then hands it to a single seam: a `WebMcpTransport` interface with one method to publish a tool and one to withdraw it. Everything the package could ever do to a browser goes through that seam and nowhere else. The registry itself imports no web library, holds no `BuildContext`, and runs unmodified on the Dart VM, which is what makes the tests cheap.

Two transport implementations ship in the skeleton. The default on any non-web target, and the fallback on web when detection fails, is a no-op transport that records the call and emits one log line stating that the tool was registered in-process but not published to a browser. The second is a web-only implementation, in the single file permitted to import `dart:js_interop`, `dart:js_interop_unsafe` and `package:web`, which implements the dual, non-throwing feature detection for both candidate entry points using the extension-with-external-members pattern the research settled on. In this phase, its publish and withdraw methods log and return without touching the browser API; making the real call is a separate work item, because the handler contract is still moving. A conditional export picks the right default at compile time so that VM tests never load the interop file.

The differentiating capability — navigation tools generated from a router — appears in the skeleton as a seam with a working, router-independent implementation: a route-descriptor type, a route-source interface, a static route source that takes an explicit list, and a generator that turns descriptors into registered tools with a fixed naming rule. The adapter that reads `GoRouter.configuration.routes` and flattens shell and nested routes is out of scope; it is a second implementation of an interface that exists and is tested by then.

## Why this approach

**Package name.** The name is `webmcp_pilot`. The pub.dev name `flutter_webmcp` is taken by an actively maintained 160/160 package and cannot be reused. `webmcp_flutter`, the research phase's working title, is rejected: it is a transposition of the incumbent's name, which reads as a squat, produces permanent confusion in search results and issue reports, and signals no difference in purpose. `flutter_mcp_router` and similar router-first names are rejected because they bury the term users actually search for. `webmcp_pilot` keeps `webmcp` discoverable and uses "pilot" for the thing this package is about: something that drives the application — navigating it and triggering its actions — rather than merely exposing a list of callable functions. Availability on pub.dev is `[UNVERIFIED]` and is checked in step 1; if the name is taken, the fallback is `webmcp_autopilot`, and the substitution is recorded in `STATE.yaml` rather than reopened as a design question.

**Differentiation.** Three concrete commitments, so this is not the incumbent under another label. First, router-first: the primary integration path is to hand the package a route source and get one navigation tool per route, rather than hand-registering each tool; the seam for this is in the skeleton and the `go_router` adapter is the next work item. Second, dev-time agent tooling as a first-class target: the transport is an interface precisely so a second, non-browser transport can expose the same tool set to an agent driving the app during development, in browsers that have no WebMCP support at all — which is every browser most of the time, given the origin-trial status. Third, no widget tree required: tool definitions, name validation and navigation-tool generation are all unit-testable on the Dart VM without pumping a widget, which the incumbent's widget-scope-centred design does not offer. Commitments one and three are partly delivered by this skeleton; commitment two is delivered by the seam that makes it additive. The claim that these are gaps in the incumbent rests on its published description only, not a code diff, and is marked `[UNVERIFIED]` until that diff is done.

**Registry shape.** Static facade over a singleton, per the research's chosen option: minimum integration cost, no `pumpWidget` in tests, no `BuildContext`, reusable outside Flutter. The `InheritedWidget` alternative was rejected in research because it buys nothing for route-table introspection and makes every test a widget test. The hybrid with an optional widget lifecycle wrapper remains the eventual shape and is out of scope here.

**Browser layer deliberately inert.** The alternative — implementing the real `registerTool` call now — was considered and rejected. The research established that the entry point differs between the IDL and the explainer, that the handler signature has already changed once, and that no source confirms what the shipped origin-trial binary exposes. Writing that call now means writing it against a guess and having no way to test the guess in CI, where no browser has the feature. Detection-only is testable today, and the seam means the eventual implementation touches one file.

**Package at the repository root rather than under `packages/`.** A nested layout was considered for tidiness against the existing `wiki/` and `.claude/` directories. It was rejected because it adds a path level to every command, every CI working directory and every future `pana` invocation, in exchange for cosmetic separation in a repository that will hold exactly one package.

**Lockfile policy.** The root library package's `pubspec.lock` is not committed, following Dart's convention for published packages, where a committed lock hides broken version bounds. The example application's `pubspec.lock` is committed and is the reproducibility anchor for the runnable entry point, and CI additionally pins the Flutter channel. Committing both was rejected; committing neither loses reproducibility of the one thing that actually runs.

## Interfaces and shared decisions

**Package name.** `webmcp_pilot`, with `webmcp_autopilot` as the recorded fallback if step 1 finds the first taken. Every identifier, import path and document uses the chosen name consistently.

**Library structure.** One public library file, `lib/webmcp_pilot.dart`. It exports the facade, the tool type, the handler alias, the exception types, the transport interface, the no-op transport, the route descriptor type, the route source interface, the static route source and the navigation-tool generator. Nothing else is public. All implementation lives under `lib/src/`, grouped into a registry group, a transport group and a routing group.

**Registry facade.** A class named `WebMcp` with a private constructor and static members only. It offers: register a tool, unregister by name, invoke by name with an input map, read the registered tools as an unmodifiable list in insertion order, install a transport, read the active transport's stable string identifier, query whether the active transport reports browser support, set a log sink, and reset. Register, unregister and invoke are asynchronous; list, the active-transport identifier, support query and transport installation are synchronous. Reset clears the tools, restores the default transport and restores the default log sink, and exists so tests do not leak state between cases. The active-transport identifier is what AC-010 reads to establish that a rejected installation left the previously active transport in place — without it, that criterion has nothing observable to assert against.

**Tool definition.** A value type named `WebMcpTool` with a required name, an optional title, a required description, an input schema defaulting to an empty JSON object map, and a required handler. The handler takes a decoded input map and returns a future of a nullable object. The handler signature deliberately omits the abort-signal parameter that the current IDL shows, because that part of the contract has already changed once; adapting the Dart handler to whatever the browser expects is the transport's job, not the application author's.

**Name rule.** A tool name is between one and 128 characters, each an ASCII letter, digit, underscore, hyphen or period. Anything else is rejected at registration.

**Transport seam.** An interface named `WebMcpTransport` with four members: a stable string identifier for logging, a synchronous boolean reporting whether the target exposes a usable model context, an asynchronous publish taking a tool definition, and an asynchronous withdraw taking a tool name. The verbs are publish and withdraw, distinct from the registry's register and unregister, so a log line or a stack trace names the layer unambiguously. Two implementations ship: `NoopWebMcpTransport`, which reports no support and records calls, and a web-only detection transport, which performs dual entry-point detection and, in this phase only, logs instead of calling the browser. A conditional export selects the default per target so the interop file never loads on the Dart VM.

**Transport installation ordering.** Installing a transport while any tool is registered throws a state error and leaves the active transport unchanged. Transports are installed before tools, and there is no republish-on-swap behaviour to reason about.

**Error handling.** A base exception type for the package, with two subtypes: a registration exception, thrown for an invalid tool name, a duplicate tool name and a navigation-tool name conflict; and a not-found exception, thrown when invoking an unregistered name. Unregistering an unknown name is not an error — it returns normally and changes nothing, so teardown paths need no existence check. The absence of WebMCP in the browser is not an error at any level: registration succeeds, the tool is held in the registry, the support query reports false, and exactly one log line is emitted.

**Logging.** A single configurable sink taking one string. The default forwards to the Dart developer log channel under the package name; the package never prints directly. Every message is one line, prefixed with the package name. The message emitted when a tool is registered without browser support names the tool and contains the words "not published", and tests assert on that substring rather than on the whole sentence.

**Routing seam.** A route descriptor carries a path pattern, an optional name, an optional description and a list of parameter names. A route source is an interface with one member returning a list of descriptors. `StaticRouteSource` takes an explicit list and returns it. The generator takes a route source and a navigation callback, and registers one tool per descriptor. The generated tool name is the word `navigate`, an underscore, and the descriptor name if present, otherwise the path pattern with every character outside the permitted set replaced by an underscore. Parameters become string properties in the generated input schema; no type inference is attempted. Generation validates every generated name against the rule and against the existing registry before registering anything, so a conflict leaves the registry untouched.

**Configuration.** The package has no configuration file and reads no environment variable. The only settable knobs are the transport and the log sink, both through the facade.

**Check command contents.** Six stages, each preceded by a printed banner naming it: dependency resolution at the root and in `example/`; a format check scoped to `lib/`, `test/`, `example/lib/` and `example/test/` (not the whole repository tree, so generated output under `example/build/` or `.dart_tool/` is never walked) that fails on any file in those four directories that would change; a single static-analysis invocation from the repository root with infos fatal, which reaches `example/` as its own nested analysis context under its own relaxed rule set without a second invocation; the root test suite; the example test suite; the wiki linter. First failure stops the run, names the failed stage in the script's own output, and sets a non-zero exit.

## Rollback

Every artifact in this work item is a new file, except three additive edits: a new level-1 section inserted at the top of the existing `README.md` (whose prior content is preserved untouched, at its current heading level, below the insertion — see step 2), a second job appended to `.github/workflows/checks.yml`, and new entries in `.gitignore`. Rollback is reverting the implementation commit, which removes the package, the example, the tests and the check script; restores `README.md` and `.gitignore` to their current content; and restores the workflow file to its current single-job form. No data is written, no external service is contacted, no package is published, no secret is provisioned, and nothing outside this repository changes. There is no one-way door in this work item and nothing here needs escalation before implementation. The one decision that would become expensive to reverse — publishing the chosen name to pub.dev — is explicitly out of scope, and `publish_to: none` in the root manifest is the mechanical guard that keeps it that way until a later work item removes it deliberately.

## Out of scope

- The real browser call. Publishing a tool to `document.modelContext` or `navigator.modelContext`, adapting the handler signature, mapping the abort signal, handling the tool-change event, and anything touching `outputSchema`. The skeleton detects and logs; it does not register with the browser.
- The `go_router` adapter. Reading `GoRouter.configuration.routes`, recursing shell and nested route types, flattening them into descriptors, and inferring parameter types from path patterns. The interface those will implement is in scope; the implementation is not.
- The optional widget lifecycle wrapper that registers and withdraws a tool from `initState` and `dispose`.
- Per-screen tool shadowing. The skeleton has one flat namespace; a name resolves the same way regardless of the active screen.
- Publishing to pub.dev, and chasing a `pana` score. The layout is structured to score well later; no score is measured or claimed in this work item.
- A non-browser dev-time transport. The seam that makes it additive is in scope; the transport itself is a later work item.
- Typed input decoding, code generation, schema derivation from Dart types, and any dependency injection framework.
- Naming the check command in `AGENTS.md` and writing the stack ADRs. Both belong to the document phase of this work item and are governed by the `bootstrap-product` skill's step 5.

## Verification approach

Most criteria in `02-criteria.md` are checked by a command whose exit code decides the outcome, each with an injected negative case that must produce a non-zero exit before the positive result counts. Three are not: CI's two-job independence (AC-020) is checked by reading job results on a pushed branch, not a local exit code; the wall-time budget (AC-022) is checked by timing a run rather than by its exit code; and the secret half of the network/secret criterion (AC-023) is checked by a manual diff review, recorded in the implementation validation report, rather than by a scan. Each of these three is described in its own paragraph below rather than folded into the general rule.

Resolution, layout and metadata criteria are checked by running dependency resolution from a clean checkout in the root and the example, and by asserting the presence of the six pub-layout paths; the negative case is a transient edit introducing an unresolvable version bound, which must fail resolution.

Behavioural criteria — registration, ordering, name validation, unregister idempotence, unknown-tool invocation, transport call routing, install-transport ordering, graceful absence with its log line, and navigation-tool generation with its conflict case — are checked by the root test suite using a fake transport and a capturing log sink installed in setup and cleared by reset in teardown. Each has a paired case that asserts a throw or an unchanged registry, so no criterion rests on a happy path alone.

Interop isolation is checked by a test that scans the source files under `lib/` and fails if a web-only or legacy interop library is imported outside the one designated file; its negative case is a transient import added to the registry file, which must make that test fail. The network/secret criterion is checked by a second scan test over `lib/` and `example/lib/` that fails on an HTTP or socket import, paired with a manual diff review for literal secrets; its negative case is a transient HTTP-client import added to any file in either tree, which must make that scan fail.

The runnable entry point is checked by a web build of the example exiting zero and emitting its build output, and by a widget test asserting the two on-screen strings. The negative case is a transient rename of a public API member in the example, which must break the build.

Toolchain criteria are checked by running the check script on a clean tree for the positive result, and by three separate injections for the negative results: unformatted whitespace, an analysis violation, and an inverted test assertion. Each injection must make the script exit non-zero and must name the failing stage; the captured output is pasted into the implementation validation report. CI is checked by pushing the branch and reading both job results, and the wiki linter is run locally as well as in CI.
