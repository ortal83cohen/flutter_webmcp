# Plan: Author argument schema, generated metadata, and agent-visible decode errors

## Goal

After this change a browser agent sees, and can act on, what the library already enforces. A manual tool built from a declared field list publishes a descriptive JSON schema derived from that same field list instead of an empty one, so the schema an agent reads and the check the decoder runs can no longer disagree by accident. A declared-field decode failure tells the agent which argument key failed and which of three closed reasons it failed for, without disclosing the rejected value, the argument map, a message or a stack. A generated domain action can carry the display title, the debugging hint and the origin list that a hand-written tool has always been able to carry. A `WebMcpAction` can declare its field list and get library-enforced decoding before its callback runs, on the same terms as `WebMcpTool.withDecodedArguments`. Nothing in the registry begins validating arguments against a schema, and no existing tool changes behaviour unless its author opts in.

## Approach

The work is four additive slices, sequenced because they are not safe to implement in parallel. The schema slice and the decode-detail slice both edit `lib/src/webmcp_typed_input.dart`, `test/registry_test.dart` and `test/webmcp_public_surface_test.dart`. The generator slice owns the annotation package, the generator and the generator example. The widget slice owns `lib/src/widgets/webmcp_action.dart` and `test/widget_layer_test.dart`, and it depends on the decoding factory from the first slice. Implementation runs those three file groups in that order, one owner at a time, with no task marked parallel.

The first slice adds a pure schema-derivation function beside the existing decoder in `lib/src/webmcp_typed_input.dart`. It turns a list of `WebMcpInputField` into the same object-schema shape the generator already builds in its private `_schemaFor` method: an object with `additionalProperties` false, a property entry per declared key, and a required list naming the required keys. `WebMcpTool.withDecodedArguments` in `lib/src/webmcp_tool.dart` calls it at construction time when, and only when, the supplied `inputSchema` map is empty, which is the default. A non-empty author-supplied map is passed through to the inner `WebMcpTool` untouched, exactly as today. Derivation happens once inside the factory, never during invocation, so the product contract's prohibition on runtime JSON Schema validation is untouched. The derivation mirrors the shape-to-schema mapping the generator's private `_TypeShape.schema` getter already performs, so a manual tool and a generated tool describing the same value describe it the same way.

The second slice threads three optional metadata fields through the generator. `WebMcpDomainAction` in `packages/webmcp_flutter_annotations/lib/webmcp_flutter_annotations.dart` gains optional, final, null-defaulting `title`, `debugging` and `exposedTo` fields, keeping its constructor const. In `packages/webmcp_flutter_generator/lib/src/webmcp_domain_action_generator.dart`, the private `_readMethod` reads them through the constant reader's peek method, the private `_ExposedMethod` record carries them, and the private `_emitClass` emits each one only when it is non-null: title and origin list as arguments to the emitted `WebMcpTool` literal, and the debugging hint inside the emitted `WebMcpToolAnnotations` literal. Because emission is conditional, every existing annotated method regenerates byte-identical output. The generator still does not construct services and still grants no authorization.

The third slice gives the manual decode path a field key and a closed reason. A new enum named `WebMcpDecodeFailureReason`, with values missing, unknown and type, is added to `lib/src/webmcp_exceptions.dart` beside the exception that carries it. `WebMcpInvalidArgumentsException` keeps its existing const no-argument constructor untouched and gains a second, named, non-const constructor that takes the failed key and the reason, exposes both as public properties, and builds the inherited details map from them. Every throw site in `webMcpDecodeArguments` and its private `_decodeValue` helper in `lib/src/webmcp_typed_input.dart` switches to the new constructor, and `_decodeValue` gains a parameter carrying the top-level argument key so a nested list or map failure still names a key the caller actually sent. The publisher is not touched: its existing details branch already serializes an accepted details map, and a two-entry string map sits far inside its size and shape limits. The generated-tool path is deliberately left alone.

The fourth slice adds an optional field list to `WebMcpAction` in `lib/src/widgets/webmcp_action.dart`. The constructor rejects a field list paired with the one-argument callback by throwing an argument error, since the decoding factory sets only a call handler. The once-guarded registration block in the state class reads the field list alongside the other descriptor values and, when it is non-null, builds the registered tool through `WebMcpTool.withDecodedArguments` instead of the plain constructor, passing a call handler that still dereferences the live widget so the newest callback of the chosen kind runs after a successful decode. The registration guard, the descriptor freeze, the unchanged child, the ownership rule on dispose and the deliberate refusal to let a disabled child disable the tool are all left exactly as they are.

## Why this approach

For schema derivation, the research considered leaving the author to hand-write both a field list and a schema, and considered always replacing a supplied schema with a derived one. The first was rejected because the two can silently disagree, which is the whole defect: the agent reads a description that is not the check the decoder runs, and the research found no existing example in the repository that keeps a hand-written pair in step. The second was rejected because it destroys the author's ability to add per-property descriptions, examples or richer constraints that the field list cannot express. Deriving only into the empty default keeps the fix automatic for the common case and keeps the override for the uncommon one.

For generated metadata, the research considered leaving the annotation alone and considered a second annotation type carrying publication metadata. Leaving it alone was rejected because the gap is purely mechanical and forces an author to abandon the generator entirely for any tool that needs a title or an origin filter. A second annotation was rejected because splitting one tool descriptor across two annotations adds reading, merging and documentation work without enabling anything the single extended annotation cannot do.

For the decode failure payload, the research considered keeping the empty failure and considered including the rejected value next to the key. Keeping it empty was rejected because the agent cannot tell a missing key from a wrong type and so has no basis for a repair attempt. Including the value was rejected outright: the product contract requires the publisher to omit the exception message and stack, and a closed reason plus a key is the largest payload that adds repair information while disclosing nothing the caller did not already send.

On the exception's constructor shape the plan departs from the research's sketch. The research assumed the existing constructor would become non-const and every call site would drop its const keyword. This plan instead keeps the const no-argument constructor and adds a named one, because the exception type is exported from the package's public library and a consumer may already construct it in a const context; a named addition is source-compatible where a signature change is not, and it also lets the details map be built in an initializer list, which a const constructor cannot do because the reason's name string is not a constant expression.

For the widget, the research considered leaving decoding to the author inside the callback and considered a separate decoded-action widget. Author-side decoding was rejected because parity with the decoding factory requires the decode to be a library-enforced step rather than a convention an author can forget. A separate widget was rejected because the two would share the entire registration, freeze, ownership and disposal lifecycle, and duplicating that lifecycle to add one optional parameter is a larger surface for no new invariant.

For the generated decode-error path the plan deliberately changes nothing. The research established that the generated invoker catches its own format exception and returns an invalid-arguments envelope that already reaches the agent, and that throwing the library exception instead would produce byte-identical wire output while changing the operation outcome from completed to handler-failed and the log kind from invoked to invocation-failed. That is an operational-accuracy change with no agent-visible benefit, so it stays out, and a criterion locks the current return behaviour so a later edit cannot drop it silently.

## Interfaces and shared decisions

**Derivation trigger.** Derivation happens when the `inputSchema` argument to `WebMcpTool.withDecodedArguments` is empty, which covers both an omitted argument and an explicitly empty map. A map with at least one entry is stored unchanged and no derivation runs. The plain `WebMcpTool` constructor never derives anything, so a handler-only tool with no schema still carries an empty one.

**Derivation function.** The function is named `webMcpSchemaFromFields`, lives in `lib/src/webmcp_typed_input.dart` beside `webMcpDecodeArguments`, and is therefore part of the package's exported public surface, because that file is exported wholesale from `lib/webmcp_flutter.dart`. This is deliberate: it is the sibling of the already-public decoder, it is pure, and an author who wants to supply an enriched schema can start from the derived one. An unexported helper file was rejected because a library-private top-level function in the typed-input file would not be reachable from the tool file at all, Dart privacy being per library.

**Schema shape.** The object wrapper is a type of object, an `additionalProperties` value of false, a properties map, and a required array present only when at least one field is required. Per-shape property schemas are: a type of string; a type of boolean; a type of integer carrying the same inclusive minimum and maximum the decoder enforces, expressed through the existing exported bound constants; a type of number for the finite double, with no invented finiteness keyword; a type of string plus an enum array for the enumeration; a type of array plus an items entry for the list; and a type of object plus an `additionalProperties` entry holding the child schema for the map. A nullable field wraps its non-null schema in a two-element anyOf union whose second member has type null, matching the generator.

**Schema derivation edge cases.** An enumeration field's allowed-names list is emitted verbatim, including when it is empty, because the decoder accepts nothing in that case and an empty enum array says so. A list or map field whose child is null emits only the base array or object type with no items or `additionalProperties` entry, because there is no child to describe; the decoder's existing rejection of such a field at invocation time is left unchanged. When two fields declare the same key, the properties map keeps the later declaration, because a JSON object cannot hold two entries for one key. That is not a claim that the decoder ignores the earlier field. The decoder still walks every field, and this change does not alter that walk. Duplicate keys are not a supported author input and get no acceptance criterion. For a nested child field only the shape, the nullable flag, the allowed names and the further child are read; its key and its required flag are ignored, because a list element and a map value are not keyed arguments.

**Schema mutability.** Derivation allocates fresh maps and lists on every call, so two tools built from one field list share no nested state. The outer map continues to be shallow-copied and wrapped unmodifiable by the `WebMcpTool` constructor. Deep schema immutability remains a declared product omission and this change does not introduce it.

**Failure reason enum.** The enum is named `WebMcpDecodeFailureReason` with exactly three values, in the order missing, unknown, type. It lives in `lib/src/webmcp_exceptions.dart`, not in the typed-input file, so the exception that carries it does not have to import the typed-input file and the existing one-way import direction between the two files is preserved. The string that reaches the agent is the enum value's own name, so the three strings are missing, unknown and type.

**Reason assignment.** An argument key that no field declares is reason unknown. A declared required key absent from the argument map is reason missing. Everything else is reason type: a null value for a field that is not nullable, a value of the wrong Dart type, an integer outside the inclusive safe range, a non-finite double, a string that is not in the allowed-names list, a non-list value for a list field, a non-map value for a map field, a non-string key inside a map value, and a list or map field declared with no child.

**Reported key.** The reported key is always a top-level argument key. For reason unknown it is the caller-supplied key verbatim. For every other reason it is the declared key of the top-level field being decoded, including when the failure occurs inside a nested list element or map value; the nested child's own declared key is never reported, because the details map has to name something the caller actually sent for the information to be usable.

**Details payload.** The details map has exactly two entries, both strings: the key under the name field, and the reason name under the name reason. It never contains the rejected value, the argument map, a free-form message, a stack, or any further entry. The exception also exposes the key and the reason as public properties, because local invocation propagates handler exceptions unchanged and a Dart caller needs the typed values rather than a serialized map.

**Exception compatibility.** The existing const no-argument constructor of `WebMcpInvalidArgumentsException` stays, keeps producing null details, and keeps both new properties null. The new named constructor is `WebMcpInvalidArgumentsException.withFailure`. It is non-const, takes a required key and a required reason, and is a member of the already exported exception class, so it adds no new library export. The public-surface test therefore names the enum and the schema function, not this constructor. The inherited code stays the invalid-arguments string and the inherited retryable flag stays false in both constructors.

**Generator reads.** The three new annotation fields are read with the constant reader's peek method. In the pinned source_gen 4.2.4, read on an absent optional field returns a reader whose constant is null, and the throw happens when a typed accessor is then called on that reader. Peek returns null for both an absent field and a null value, so the generator calls a string, boolean, or list accessor only when peek returns a reader. The list accessor returns constant objects, and each element is read as a string. A nullable string list is readable with the installed package and no unavailable interface is assumed.

**Generator emission.** Each of the three is emitted only when non-null. The title is emitted as a string literal argument on the emitted tool, the origin list as a const string list literal argument on the emitted tool, and the debugging hint as a boolean literal inside the already-const emitted annotations literal. An origin list the author declared empty is emitted as an empty list literal, because the product contract makes a null list the omission signal and an empty list a distinct state the author chose.

**Generator validation.** An empty or whitespace-only title fails generation with an invalid-generation-source error naming the method, mirroring the existing rule for an empty description. The generator test observes that failure through the builder log callback, matching the two existing negative tests, and does not expect the test function to see a thrown error. A non-string origin-list element is not validated by the generator, because the annotation field is a list of strings and such a fixture fails to compile before generation. Neither check constructs a service nor grants authorization.

**Widget field list.** The parameter is named fields, is a nullable list of `WebMcpInputField`, and is stored as an unmodifiable copy when non-null. A non-null field list with the one-argument callback throws an argument error at construction, after the existing exactly-one-callback check. An empty but non-null field list is a declared empty field list, not an absent one: it builds through the decoding factory, accepts only an empty argument map, and derives a schema describing an object with no properties.

**Widget invariants that do not change.** The registration guard still registers once in the dependency-change callback. The descriptor's name, description, input schema, annotations, title and origin list remain frozen at the first mount, and the field list joins that frozen set. The registered call handler still dereferences the live widget, so the newest call callback runs after a successful decode. The build method still returns the child unchanged. A hidden or disabled child still does not disable the tool. Dispose still removes the registered name only when the state owns it.

## Rollback

Every slice is independently revertible and none changes stored data, a wire protocol version or a public type's existing signature. Reverting the first slice restores the empty default schema and removes one exported function. Reverting the second restores the annotation to five fields and the generator to its current emission, after which the regenerated fixture must be regenerated once more. Reverting the third restores the no-argument throw sites and removes one exported enum and one named constructor, returning the wire payload to a code and a retryable flag with no details. Reverting the fourth removes one optional widget parameter and one registration branch. The only additions to the exported public surface are one function, one enum and one named constructor, all purely additive, so a revert removes capability without altering the behaviour of code that never used it. This is not a one-way door and needs no human escalation on rollback grounds.

## Out of scope

- Changing the generator's format-exception catch, the invalid-arguments map it returns, or the operation settlement and log kind that follow from it. A criterion locks the current behaviour instead.
- Adding a field key or a reason to the generated-tool failure path.
- Generated route wrapping.
- In-flight invocation cancellation or termination of a running handler.
- Multiple Flutter view operation.
- Output schema derivation or publication of any kind.
- Reconciling a `WebMcpAction` registration on rebuild, for the field list or for any other descriptor value. The descriptor stays frozen at the first mount.
- Any runtime validation of arguments against a schema, in the registry or anywhere else.
- Rejecting a list or map field declared with no child at construction time, which would change existing construction behaviour.
- Edits to `wiki/product/webmcp-contract.md` and to `README.md`, including documenting the field key and the reason values. Those belong to the document phase.
- Deep immutability of the derived schema's nested maps.

## Verification approach

Each criterion is checked by a Dart test in the repository, and the whole set is checked by the repository check script, so the verifier runs commands rather than reading code.

The schema criteria are checked in `test/registry_test.dart` by building a tool through the decoding factory with a field list covering every shape in `WebMcpInputShape` and asserting on the resulting descriptor's input schema map, including a childless list and a childless map that construct and carry only the base type, with the negative cases supplying a non-empty author schema and asserting it survives unchanged, and building two tools from one field list and asserting a mutation through one nested property map is not visible through the other. The continued absence of runtime validation is checked by asserting that a plain handler-only tool with no schema still carries an empty one and that invocation outcomes for a field-list tool are decided only by decoding.

The generator criteria are checked in `packages/webmcp_flutter_generator/test/generator_test.dart` against the builder, with one fixture setting all three new annotation fields and asserting the three emitted members appear, and one fixture setting none and asserting none of the three member names appear anywhere in the output. The empty-title case is checked by reading the builder log for an invalid-generation-source message that names the method, the same way the existing negative generator tests do. End-to-end emission is checked in `packages/webmcp_flutter_generator/example/test/live_instance_test.dart` against a regenerated fixture. The unset-annotation criterion is the generator builder test that asserts none of the three member names appear, not a diff of the application example's generated file.

The decode-detail criteria are checked in `test/registry_test.dart` on the typed properties of the caught exception for each of the three reasons, and in `test/native_publisher_test.dart` on the encoded wire response, asserting the invalid-arguments code, the non-retryable flag, a details object with exactly the two declared string entries, and the absence of a distinctive rejected value string anywhere in the encoded response. The nested-key criterion is checked by rejecting a wrongly typed element inside a declared list and asserting the reported key is the list's own key. The generated-path lock is checked in `packages/webmcp_flutter_generator/example/test/live_instance_test.dart` by asserting the invoker returns the envelope rather than throwing and that the envelope's error object has no details entry.

The widget criteria are checked in `test/widget_layer_test.dart` by pumping an action with a field list inside a screen scope, invoking through the registry, and asserting the callback count, the decoded argument map, the rejection without a callback, the derived schema on the registered descriptor, the unchanged child, an invocation that still reaches the callback while the child is disabled, the rebuild that changes the field list having no effect, the newest callback running, and removal on unmount. The rejected pairing is checked by asserting an argument error at construction. The public surface criterion is checked by the enumerated export list in `test/webmcp_public_surface_test.dart`.

Single-file commands are used during implementation for the registry, widget, publisher and public-surface suites, and the generator package and both example packages are run with their own test commands. The final gate is the repository check script, whose stage output must be pasted as evidence; a criterion is not met until the command output that proves it is in the verification notes.
