# Acceptance criteria: Flutter WebMCP package skeleton

Scope: the project skeleton only — a toolchain that resolves, one runnable entry point, a test suite demonstrated to report failure, a formatter and linter wired in, a single check command, and CI including the wiki linter. Feature completeness of the WebMCP integration is not measured here.

Throughout, "the package name" means the name decided in `01-plan.md` (`webmcp_pilot`, or the recorded fallback if step 1 of the plan found it taken), and "the check script" means `tools/check.sh`.

## Criteria

| ID | Criterion | How it is checked | Negative case |
|---|---|---|---|
| AC-001 | When dependency resolution is run from a clean checkout at the repository root and again inside `example/`, both invocations shall exit with status 0. | Run `flutter pub get` at the root and in `example/`; read both exit codes. | Transiently change one dependency bound in the root manifest to a version that does not exist; resolution shall exit non-zero and name the unresolvable dependency. Revert. |
| AC-002 | When the repository is listed, the paths `lib/`, `test/`, `example/`, `README.md`, `CHANGELOG.md`, `LICENSE`, `analysis_options.yaml` and `pubspec.yaml` shall all exist at the repository root. | List the eight paths and assert each is present. | Temporarily move `LICENSE` aside; the presence assertion shall report a missing path. Restore. |
| AC-003 | When the root manifest is read, it shall declare the package name decided in the plan, a non-empty description, a version, an SDK constraint, a web-only platform declaration, and `publish_to: none`. | Read `pubspec.yaml` and check the six fields. | Remove `publish_to: none`; the check shall report the missing accident guard. Restore. |
| AC-004 | When a Dart program imports only `package:<package name>/<package name>.dart`, it shall be able to construct a tool, register it, list registered tools, invoke it by name, unregister it, install a transport, and construct a static route source, with no import from any `src/` path. | A test file under `test/` that imports only the public library and exercises all seven operations; `flutter analyze` and `flutter test` both exit 0. | Delete one export line from the public library file; the same test shall fail to compile with an undefined-name error. Restore. |
| AC-005 | When a tool with a valid name is registered and no tool of that name exists, the registered-tool list shall contain exactly one entry with that name, and repeated registrations of distinct names shall appear in the list in registration order. | Test registering three tools and asserting names and order. | Register a second tool whose name equals an existing one; registration shall throw the package's registration exception and the list length shall stay at 3. |
| AC-006 | When a tool name is empty, longer than 128 characters, or contains a character outside ASCII letters, digits, underscore, hyphen and period, registration shall throw the package's registration exception and the registered-tool list shall remain unchanged. | Test four rejected names, asserting both the throw and the unchanged list. | A 128-character name and a name containing a digit, an underscore, a hyphen and a period shall each register without throwing, so the rule is shown to reject only what it should. |
| AC-007 | When a registered tool is unregistered, it shall be absent from the registered-tool list, and a second unregister call for the same name shall return without throwing and leave the list unchanged. | Test the two calls and the list contents after each. | Assert that unregistering a name that was never registered returns without throwing; a version that throws shall fail this test. |
| AC-008 | When a tool is invoked by a name that is not registered, invocation shall throw the package's not-found exception; when invoked by a registered name, it shall return the value produced by that tool's handler. | Test both branches with a handler returning a known sentinel value. | The not-found branch is itself the failing case; additionally, invoking a registered name shall not throw the not-found exception. |
| AC-009 | When a fake transport is installed and a valid tool is registered, the fake shall record exactly one publish call carrying that tool's name; when the tool is unregistered, the fake shall record exactly one withdraw call carrying that name. | Test with a recording fake transport, asserting the two call logs. | Register a tool whose name is invalid; the fake shall record zero publish calls, showing that validation runs before the seam is reached. |
| AC-010 | When a transport is installed while at least one tool is registered, installation shall throw a state error and the previously active transport shall remain the active one. | Test: register a tool, attempt installation, assert the throw, then assert the active transport identifier is unchanged. | Installing a transport while no tool is registered shall not throw and shall change the active transport identifier. |
| AC-011 | When the default transport is resolved on the Dart VM, the support query shall report false, registering a valid tool shall complete without throwing, and exactly one line shall be emitted to the installed log sink containing that tool's name and the substring `not published`. | Test with a capturing log sink installed before registration; assert the support query, the absence of a throw, the line count and the substring. | Assert that zero lines, more than one line, or a line lacking the tool name fails the test; additionally, a handler that throws inside registration shall not be required, so a version that throws on absent browser support fails this criterion. |
| AC-012 | When the source files under `lib/` are scanned, exactly one file shall import a web-only library (`dart:js_interop`, `dart:js_interop_unsafe` or `package:web`), and no file shall import `dart:html` or `dart:js`. | A test that scans `lib/` recursively and asserts the two conditions, naming the one permitted file. | Transiently add a `package:web` import to the registry implementation file; the scan test shall fail and name that file. Revert. |
| AC-013 | When a static route source containing three descriptors is passed to the navigation-tool generator with a recording navigation callback, three tools shall be registered whose names follow the naming rule stated in the plan, and invoking one of them shall record exactly one navigation call carrying that descriptor's path. | Test the generated names, the registered count and the recorded navigation call. | Supply a descriptor whose generated name collides with an already-registered tool; generation shall throw the registration exception and the registered-tool count shall equal the count from before generation. |
| AC-014 | When `flutter build web` is run inside `example/`, it shall exit with status 0 and produce `example/build/web/index.html`. | Run the build; read the exit code and check the file exists. | Transiently rename a public member used by the example's registration call; the build shall exit non-zero with an undefined-name error. Revert. |
| AC-015 | When the example's single screen is pumped in a widget test, the rendered output shall contain the text of the registered tool's name and a text stating that no model context was detected, and the registered-tool count shall be exactly one. | `flutter test` inside `example/`, asserting two finders and the count. | Change the example to register a second tool; the count assertion shall fail. Revert. |
| AC-016 | When a repository-wide format check that fails on any file needing reformatting is run on a clean checkout, it shall exit with status 0. | Run the format check in the check script; read the exit code. | Insert stray indentation into one committed Dart file; the format check shall exit non-zero and name that file. Revert. |
| AC-017 | When static analysis is run at the repository root with informational diagnostics treated as fatal, it shall exit with status 0 and report no issue in `lib/`, `test/` or `example/`. | Run the analyzer stage of the check script; read the exit code and the issue count. | Add a public member without a documentation comment and an unused import to one file in `lib/`; analysis shall exit non-zero and report both, showing the strict rule set is active. Revert. |
| AC-018 | When one assertion in a named test under `test/` is inverted, the test suite shall exit non-zero and its output shall name that test; when the assertion is restored, the suite shall exit 0. | Perform the inversion, capture the failing output and exit code, restore, rerun. Paste both outputs into the implementation validation report. | The inverted run is the negative case; a suite that exits 0 with the assertion inverted fails this criterion outright. |
| AC-019 | When the check script is run on a clean checkout, it shall run, and print a named banner for, dependency resolution, the format check, static analysis at the root, static analysis inside `example/`, the root test suite, the example test suite and `python3 tools/lint_wiki.py`, and exit with status 0. | Run the check script; read the exit code and confirm each of the seven named stages appears in its output. | Each of the three injections from AC-016, AC-017 and AC-018 shall, run through the check script, produce a non-zero exit and print the name of the stage that failed. |
| AC-020 | When the CI workflow file is read, it shall define a job that installs the Flutter stable channel and runs the check script, and shall retain a separate job running `python3 tools/lint_wiki.py`; when the branch is pushed, both jobs shall report success. | Read `.github/workflows/checks.yml`; read the two job results on the pushed branch. | Transiently add a `needs:` dependency from the wiki job onto the package job; push a branch touching only a file under `wiki/`. The wiki job shall then wait on the package job's Flutter install before it can start, which is observable as a delayed or blocked wiki-job run rather than the immediate independent result the positive case produces. Revert the workflow file. |
| AC-021 | When `python3 tools/lint_wiki.py` is run at the repository root, it shall exit with status 0. | Run the command; read the exit code and output. | The linter shall exit non-zero if a fenced code block is present in `01-plan.md`, if a work-item number is duplicated, or if an acceptance criterion uses a vague term; these are the linter's own checks and are exercised by its existing rules. |

## Non-functional criteria

| ID | Criterion | How it is checked | Negative case |
|---|---|---|---|
| AC-022 | When the check script is run a second time on an unchanged tree with dependencies already resolved, it shall complete in under 180 seconds of wall time on a developer machine. | Time the second run; record the measured figure in the implementation validation report. | A run exceeding 180 seconds fails this criterion; 180 seconds is a budget fixed here in the criteria, not a measured baseline, and the measured number is recorded whether or not it passes. |
| AC-023 | When the source files under `lib/` and `example/lib/` are scanned, no file shall import an HTTP or socket library, and no file shall contain a credential, token, key or personal email address. | A scan for network-library imports plus a review of the diff for literal secrets. | Adding an HTTP client import to any file under `lib/` shall make the scan fail; the skeleton contacts no network endpoint at runtime. |
| AC-024 | When the package is used on a target with no browser model context, no code path shall throw for that reason alone: registration, unregistration, listing and invocation shall all complete, and absence shall be observable only through the support query and the log line. | The VM test suite exercises all four operations with the default transport and asserts no throw. | A build in which absent browser support raises an exception from registration shall fail AC-011 and this criterion together. |

## Explicitly not required

- Calling the browser's tool-registration method, adapting the handler signature, handling the abort signal, or reacting to the tool-change event. The skeleton detects the browser surface and logs; it does not publish to it.
- Any `go_router` dependency, route-table flattening, shell or nested route handling, or parameter-type inference from path patterns.
- The optional widget lifecycle wrapper, per-screen tool shadowing, and typed input decoding.
- A `pana` score, documentation coverage above what the enabled lint enforces, or publication to pub.dev.
- A non-browser dev-time transport implementation.
- A `## Checks` section in `AGENTS.md` and the stack ADRs; both belong to the document phase of this work item.
- Running the example against a browser that actually exposes WebMCP. No such browser is assumed available in development or CI, and no criterion depends on one.
