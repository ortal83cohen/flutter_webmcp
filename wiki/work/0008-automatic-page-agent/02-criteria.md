# Acceptance criteria: Automatic page content and actions

## Frozen

- Frozen at: not yet.
- Frozen by: not applicable; this work item delivers a plan only.
- These are future implementation acceptance criteria. No runtime behavior, spike, test, benchmark, or generator compatibility result is claimed as completed by this planning artifact.

## Criteria

| ID | Criterion | How it is checked | Negative case |
|---|---|---|---|
| AC-001 | Before implementation interfaces freeze, a semantics spike shall record exact Flutter/Dart versions and prove scope isolation in debug, profile, and release on the declared Flutter 3.47.0 baseline and a selected upper test version, including siblings, nesting, merging, exclusion, routes, modals, disposal, and multiple views. Unsupported cases shall disable automatic exposure with diagnostics; an unproven baseline blocks shipping automatic semantics. | Archive commands, raw output, fixture observations, and the support matrix; the installed Flutter 3.38.4 may inform research only. | Force an ambiguous boundary or run only 3.38.4; the gate cannot pass and no ancestor-wide fallback is enabled. |
| AC-002 | Before browser interfaces freeze, a transport spike shall record the supported draft/browser matrix and demonstrate real secure-context registration, invocation, safe results/errors, cancellation, unregistration, annotations, and both JavaScript and WebAssembly builds or an explicitly documented unsupported build. | Capture actual browser version, flags/trial requirements, commands, output, and an invocation trace; failing optional fields are omitted only with documented compatibility behavior. | A browser with a present but nonfunctional modelContext property is diagnosed as unusable; property detection alone never passes the gate. |
| AC-003 | When a consumer enables the bridge once and mounts one opted-in page wrapper with a page identifier and child, standard labeled content and supported actions shall become readable/invokable without per-widget tool descriptors, schemas, annotations, inheritance, or code generation. Standard ModalRoute activation is automatic; unsupported navigation requires an explicit activity source before exposure. | Run the minimal example and inspect its integration surface and agent-visible snapshot. | An unwrapped page and an unsupported navigation setup without an activity source expose no automatic page data or actions. |
| AC-004 | When read is invoked, the page protocol shall return its schema version, page identifier, mount token, revision, activity, coverage metadata, and bounded node records containing opaque handles, parent references, role, permitted label/hint/value/state/actions, with optional selected geometry. Act shall accept the same mount/revision plus a node handle, action, request identifier, and action arguments. | Schema and protocol tests cover required, optional, and rejected fields and read-act-read behavior. | Malformed arguments, raw semantics node IDs, unknown fields, and unknown actions produce invalidArguments or unsupportedAction without dispatch. |
| AC-005 | When a wrapper rebuilds, changes semantic state, deactivates, replaces its source, or unmounts, its immutable snapshots and handles shall obey the documented mount/revision rules; no action shall dispatch using a stale, foreign, disposed, or inactive handle. | Race fixtures change state between read and act and remount an identically named page. | Reuse a previous mount token, changed revision, or sibling handle; receive scopeGone, staleSnapshot, or unknownHandle and observe no callback. |
| AC-006 | When pages are nested or share a view, nodes shall belong to their nearest opted-in wrapper; sibling scopes shall not overlap. Covered routes and background pages shall reject actions and reads. An unwrapped blocking modal suspends the underlying page; a separately wrapped modal exposes only its own scope. | Navigate, open/close nested and root-navigator dialogs, and inspect both discovery and retained handles across transitions. | Attempt a background action through a previously discovered tool or request content from a covered page; receive inactiveScope with no disclosure or callback. |
| AC-007 | When a current in-scope node advertises an allowed action and is not disabled, hidden, blocked, or detached, act shall revalidate and dispatch at most once per request identifier within its mount; successful dispatch returns a receipt rather than a claim of completed application work. | Positive tap, toggle, increment/decrement, and scroll fixtures, delayed handlers, duplicate requests, and cancellation races. | Disable or remove a node after read, repeat the request identifier, or cancel before dispatch; no second or forbidden callback occurs. |
| AC-008 | When inputs or sensitive content exist, default snapshots shall omit editable values and input mutation, obscure password/sensitive nodes, and never infer arbitrary labels to be safe. Explicit subtree exclusions and field-level opt-ins shall control disclosure; obscured values remain prohibited. | Synthetic secrets in labels, editable fields, excluded subtrees, errors, and diagnostics; inspect all wire outputs. | A setText request without explicit node opt-in, or an obscured value opt-in, is refused without exposing the value. |
| AC-009 | When snapshots exceed limits, traversal shall stop at the documented resource budgets, return explicit partial coverage and omission metadata, and paginate only the captured materialized window using revision-bound cursors; scrolling requires a refreshed snapshot. | Large semantics fixture tests the proposed defaults of 200 returned nodes, 1,000 visited nodes, depth 32, and 64 KiB UTF-8 per response; query operates only on permitted fields in captured data. | Expired cursors, oversized limits, and attempts to fetch unbuilt rows are rejected or explicitly partial; no total-data completeness is implied. |
| AC-010 | When the native publisher attaches, existing and later registry tools shall be mirrored; duplicate attach, first-live-name wins, scope removal, detach, and explicit bridge cleanup before reset shall preserve existing local ownership and custom transport behavior. | Registry/transport integration tests exercise existing manual tools and each lifecycle transition. | Browser registration failure does not remove local tools or falsely mark them published; a skipped duplicate cannot unregister the winner. |
| AC-011 | When a browser invokes a published tool, the bridge shall enforce bounded JSON-safe input/output, sanitize exceptions, propagate cancellation state, and keep same-origin exposure by default. Local invocation retains its current raw result/exception contract. | Real-browser and Dart tests compare local and browser results, permission failures, cancellation, non-finite/cyclic/unsupported values, and handler exceptions. | Invalid wire data, denied policy, or cancelled-before-dispatch calls return a safe failure without leaking stack traces, secrets, or invoking the handler. |
| AC-012 | When optional domain generation is added after the MVP gates, annotations shall expose only opted-in public instance methods through a generated WebMcpToolSource adapter bound to a supplied live object. Decoding shall support only the documented primitive, enum, nullable, and bounded collection types and reject unsupported signatures at generation time. | Positive and diagnostic golden fixtures plus dependency solve on the declared SDK/analyzer matrix; generated adapters are invoked against two distinct live objects. | Private/static/generic methods, callbacks, arbitrary objects, unsupported map keys, missing required arguments, and unknown fields fail with actionable diagnostics or safe argument errors. |
| AC-013 | When a generated source depends on state initialized after super.initState, supplying it through the wrapper during build shall register after mounting without reading an uninitialized field; identity replacement removes only previously owned tools and installs the new instance source. Every domain invocation still executes application authorization. | Widget lifecycle, source replacement, duplicate-name, revoked-role, and disposed-service fixtures. | The generator never constructs the service or bypasses a denied authorization check; late or disposed sources cannot continue invoking an obsolete instance. |
| AC-014 | When the MVP is exercised with a real browser agent or an explicitly identified native browser-agent harness, discovery shall find the published page tools, read shall identify a labeled control, act shall trigger its permitted effect, and a fresh read shall observe that effect. The unsupported-browser example shall remain usable manually. | Preserve a reproducible discover-read-act-read trace, native transport evidence, and an unsupported-browser run; a mock registry-only test cannot substitute. | Repeat against an inactive page, stale handle, and absent native API; actions are refused and normal Flutter interaction remains usable. |

## Non-functional criteria

| ID | Criterion | How it is checked | Negative case |
|---|---|---|---|
| AC-015 | When support, ownership, privacy, coverage, or publication is incomplete, developer diagnostics shall expose safe reason codes, counts, capabilities, collisions, build/browser versions, and truncation state without content values or arguments by default. | Inspect diagnostics for all omission classes, with unknown counts represented as unknown. | An intentionally inaccessible platform view or excluded subtree cannot appear as fully discovered; synthetic secret content never appears in default logs. |
| AC-016 | When the wrapper and bridge are detached repeatedly, semantics handles, listeners, callbacks, owned registrations, and pending invocations shall be released or invalidated; disabling the feature restores manual-only behavior. | Repeated mount/unmount and attach/detach fixtures; explicit cleanup then reset; rollback walkthrough. | A disposed wrapper or detached bridge cannot retain an invokable tool or publish a later registry change. |
| AC-017 | Before a release claim, the team shall record measured snapshot/dispatch latency, traversal/memory limits, and build overhead against fixture size and tested environments, plus full-suite and wiki lint command output. Existing failing or unavailable checks remain visible blockers or separately approved scope findings. | Preserve measurements with methods and raw outputs; run bash tools/check.sh and the wiki linter on the actual supported SDK. | Missing measurements cannot become speed claims; the installed unsupported SDK or a failed check cannot be reported as release validation. |
| AC-018 | When public documentation is published alongside a future implementation, it shall distinguish the native-semantic MVP, optional generation, and later custom data provider stage; show manual fallback, integration/lifecycle/privacy constraints, tested support matrix, and omitted coverage. Package names below remain proposed until implemented. | Review examples and product-contract/ADR updates against observed implementation and baseline API regressions. | A claim to discover all page data, support unseen browser versions, or ship a generator/provider absent from the release fails review. |

## Explicitly not required

Implementation or runtime verification in this planning-only work item; discovery of hidden, server-only, excluded, or lazily unbuilt data; an in-page agent SDK; MCP network transport; automatic business authorization; inferred destructive-action safety; arbitrary Dart serialization; router-specific navigation generation; custom data provider delivery in the MVP; benchmark claims without measurement.
