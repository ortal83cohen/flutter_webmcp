# Plan: Tighten package publishing, tests, and onboarding docs

## Goal

After this change the webmcp_flutter archive that pub.dev receives no longer contains the packages directory or the spikes directory. A version tag pushed by any means publishes only after the full repository check suite has passed in the same tag-triggered workflow run. The public-surface test names the ten symbols in this work item's research inventory and pins the four integer constants in that inventory. It does not claim to name every export of the public library. The page action tests cover the four untested requestId boundaries: zero, the safe-integer maximum, one above the maximum, and a reused latest id with a different action. The package metadata names an issue tracker, the public library carries a library doc comment, and the example directory has a README that says how to run it and why it must run from a repository checkout. The comparison base for every unchanged-file check is commit bf6d4795e0f339043487c4f007f1365573adf762.

## Approach

Archive contents are controlled only by the root .pubignore file. Two rooted entries, one for the packages directory and one for the spikes directory, are added in a new commented group of that file. No other ignore entry changes. The example pubspec keeps its relative path dependencies on the companion packages, as decided in the research; the new example README carries the consequence to readers.

Publication gating lives in .github/workflows/publish.yml. A new job named check is added before the existing publish job. It checks out the repository, sets up Python 3.12 with the same Python setup action and version that release.yml uses, sets up Flutter stable 3.47.0 with the flutter-actions/setup-flutter action already used in publish.yml, and runs the repository check script with bash. It requests only read access to repository contents and does not request an id-token permission. The existing publish job gains a dependency on the check job and is otherwise unchanged, including its steps, its permissions, and its order of dependency install, Dart setup, dry run, and forced publish. The tag trigger and its pattern are unchanged. The header comment of the workflow is updated in words to say that publication waits for the check job. release.yml is not edited, so its own check step before tagging remains.

Test gaps close in the two existing test files. test/webmcp_public_surface_test.dart gains a reference to each of the ten inventory symbols inside its existing test, and value assertions for the four integer constants in that inventory. Other exported names that the surface test does not reference stay outside this work item. test/page/webmcp_page_test.dart gains one new widget test that drives the public page act tool through the existing private act helper and checks each of the four requestId boundaries against both the returned code and a callback counter.

Documentation changes touch three files: pubspec.yaml gains an issue_tracker field; lib/webmcp_flutter.dart gains a library doc comment attached to a library directive; and example/README.md is created. The root README is not edited.

## Why this approach

The research artifact, section Options considered, records the rejected alternatives. Excluding only spikes was rejected because the companion package sources, tests and fixtures would still ship to every consumer. Retargeting the example to hosted companion versions before excluding packages was rejected because those packages are not established as published, so version constraints would not resolve. Triggering publication from the release workflow result through a workflow_run trigger was rejected because the release pipeline page says pub.dev accepts an automated publish only from a tag-triggered run. Moving the check out of release.yml was rejected because release.yml performs its own write steps, a version bump commit and a tag push, which should stay gated. A separate unit test reaching the private act method was rejected because it needs a new access seam, and the widget tests already reach the same path through the public tool.

One choice is made here beyond the research. The check job sets up Python explicitly rather than relying on the runner image, because the check script's first stage runs the wiki linter with python3 and release.yml already pins Python 3.12 for the same script; relying on the image default would let the two runs differ silently. The root README retry sentence is not part of this work item. A sentence saying that any changed fingerprint field returns duplicateRequest would be false: a different pageId or mountToken returns scopeGone, and a non-current revision returns staleSnapshot, both before the fingerprint comparison.

## Steps

1. Edit .pubignore. Add a group with a one-line comment saying that the companion packages and spikes are repository-only, followed by one rooted entry for the packages directory and one rooted entry for the spikes directory, each written with a leading and trailing slash in the same style as the existing rooted entries. Complete when a publish dry run has no archive-tree entry whose name is packages and no archive-tree entry whose name is spikes, while it still has top-level tree entries named README.md, CHANGELOG.md and LICENSE, a tree entry named webmcp_flutter.dart nested under lib, and a tree entry named main.dart nested under example then lib. An archive-tree entry is a listing line whose prefix is box-drawing characters; prose lines such as the dependency download message are not entries.

2. Edit .github/workflows/publish.yml. Add the check job described in the approach, placed above the publish job under the jobs key, with a display name that says it runs the package check suite. Add a needs entry naming the check job to the publish job. Update the header comment to state that publication runs only after the check job passes. Complete when the file parses as YAML, the on block is byte-identical to commit bf6d4795e0f339043487c4f007f1365573adf762, the publish job steps and permissions are byte-identical to that commit, and the publish job lists the check job in needs.

3. Edit test/webmcp_public_surface_test.dart inside the existing test. Add a not-null reference for each type: WebMcpEvidenceKind, WebMcpPageErrorCode, WebMcpBindingViewProvider, WebMcpViewBinding, WebMcpViewProvider and WebMcpInputShape. Add value equality assertions: webMcpPageProtocolVersion equals one, webMcpMaxSafeInteger equals 9007199254740991, webMcpSafeIntegerMinimum equals minus 9007199254740991, and webMcpSafeIntegerMaximum equals 9007199254740991. Additionally assert that WebMcpPageErrorCode values contain invalidArguments and duplicateRequest, so the codes the new page test relies on are pinned at the public surface. Do not change the test name or the existing assertions. Complete when all ten names appear in the file and the test passes.

4. Edit test/page/webmcp_page_test.dart. Add one widget test after the existing test about stale revision, handle and request order, built from the same harness pattern: a WebMcpPage around one tappable Semantics node whose tap callback increments a counter. In this order, using one read snapshot and one node for the first four acts: act with requestId zero and assert the code is invalidArguments; act with requestId one above webMcpMaxSafeInteger, passed as an integer and not a double, and assert the code is invalidArguments; act with requestId one and action tap and assert it dispatched; act again with requestId one and action longPress and assert the code is duplicateRequest; then pump, take a fresh read of the same page, and act on the tap node of that fresh read with requestId equal to webMcpMaxSafeInteger and action tap and assert it dispatched. The fresh read keeps the final case independent of whether the first dispatch advanced the page revision. Assert the counter is zero after the two rejections, one after the first dispatch, still one after the duplicate, and two at the end. The test keeps its four existing source imports. webMcpMaxSafeInteger comes from the existing page barrel import. The test does not add an import of the public library, because placing that import beside the source imports makes the analyzer report those source imports as unnecessary. Complete when the test passes and each rejection is shown not to invoke the callback.

5. Edit pubspec.yaml. Add an issue_tracker field directly after homepage with the value https://github.com/ortal83cohen/flutter_webmcp/issues. Change nothing else, including the version. Complete when the field is present with that exact value and the dry run reports no new warning.

6. Edit lib/webmcp_flutter.dart. Above the first export, add a short library doc comment followed by a bare library directive, matching the pattern already used in lib/src/page/page.dart. The comment names WebMcp as the tool registry, WebMcpPage as optional page observation and guarded actions, and WebMcpNativePublisher as the browser publication entry point; states that browser publication is experimental; and points readers to the package README. It does not mention the annotation or generator packages as available on pub.dev. Complete when analysis passes with fatal infos and the doc comment text contains all three names and the word experimental.

7. Create example/README.md. It states what the example demonstrates, that it depends on the root package and on the annotation and generator packages through relative paths, that it must therefore be run from a clone of the repository, and how to fetch dependencies and run it in Chrome from the example directory. It states that the companion packages are not presented as published. Complete when the file exists, contains no claim that the companion packages are on pub.dev, and the dry run has an archive-tree entry named README.md nested directly under example.

8. Run the formatter with no writes and a failing exit on change, over lib, test, example/lib and example/test. Then run the analyzer with fatal infos and warnings, the two edited test files individually, the publish dry run, and the full check script. Record the outputs for the verify phase. The root README remains byte-identical to commit bf6d4795e0f339043487c4f007f1365573adf762.

## Interfaces and shared decisions

- Ignore entries are exactly the rooted directory forms for packages and spikes. No glob, no unrooted form, and no entry for any subdirectory of either.
- The new workflow job identifier is check. The publish job identifier stays publish. The check job requests contents read only. The publish job keeps id-token write and contents read. No secret is referenced by the check job.
- Toolchain in the check job: Flutter channel stable, version 3.47.0, through flutter-actions/setup-flutter at major version 4; Python 3.12 through actions/setup-python at major version 5; the command is bash invoking tools/check.sh from the repository root.
- The tag trigger pattern stays the existing three-component v-prefixed numeric pattern. No other trigger is added.
- Error codes used in tests are compared by their string wire value, as the existing page tests do, namely invalidArguments and duplicateRequest.
- The out-of-range requestId is the Dart integer one above webMcpMaxSafeInteger. It is not a double and not a string.
- The changed action used for the duplicate case is longPress, a member of the supported action set. The guard order in the act path checks the supported set and then the requestId fence and fingerprint before any policy check, so longPress is refused as a duplicate before its long-press policy is consulted.
- The issue_tracker value is the repository issues URL without any trailing path. The README link ending in the new-issue chooser stays where it is and is not copied.
- The library doc comment uses a bare library directive so the analyzer does not report a dangling doc comment.
- Documentation never states that webmcp_flutter_annotations or webmcp_flutter_generator are published on pub.dev.
- No product code under lib/src changes. No version bump and no CHANGELOG edit is made by hand; release.yml owns those.

## Rollback

Every change is a file edit in one commit and is undone by reverting that commit. Reverting the pubignore entries restores the previous archive contents on the next release. Reverting the workflow restores ungated publication. Reverting the tests and documentation has no runtime effect. The one irreversible element is ordinary to this repository: once the change is merged, release.yml publishes a new version, and pub.dev does not allow a published version to be deleted. That version can be superseded by the next release or retracted, but not removed. This is the normal behaviour of every merge to main and is not a new one-way door introduced by this work item, so it is noted rather than escalated.

## Out of scope

- Any GitHub ruleset or protected-tag configuration. The research leaves availability on this plan unresolved and the chosen enforcement is the workflow file.
- Publishing, versioning or retargeting the annotation and generator packages, and replacing the example path dependencies.
- Changes to release.yml, tools/check.sh, the bump helper, or the pub.dev trusted-publisher settings.
- Any change to product code under lib/src, including the requestId fence or the fingerprint fields.
- Any change to the contents of the packages or spikes directories.
- A new test file or a test-only access seam for the private act method.
- A manual version bump or CHANGELOG entry.
- Any edit to the root README, including a retry sentence. A universal duplicateRequest claim would not match the act path.

## Verification approach

The archive is checked by running the publish dry run from the repository root and searching its archive-tree entries, meaning listing lines prefixed by box-drawing characters, for an entry named packages or spikes. Prose lines that merely contain those words are ignored. The negative case is the same search on commit bf6d4795e0f339043487c4f007f1365573adf762, which finds both directory entries. The same listing is searched for the top-level tree entries README.md, CHANGELOG.md and LICENSE, for webmcp_flutter.dart nested under lib, for main.dart nested under example then lib, and for README.md nested directly under example.

The workflow is checked by reading publish.yml, parsing it as YAML, and comparing its on block and its publish job steps and permissions with commit bf6d4795e0f339043487c4f007f1365573adf762 through a path-scoped git diff. release.yml is checked byte-identical to that commit. The check job is read for its command, toolchain versions and permissions. Running the workflow itself on GitHub is not part of local verification; the negative case is a reasoning check that a publish job without the needs entry would be allowed to start independently.

The tests are checked by running the public-surface test file and the page test file individually and then the full check script. Each new page assertion has a negative case: the counter assertions fail if a rejected request reaches the callback, and the code assertions fail if the fence or fingerprint returns a different code. The surface test negative case is that removing one export from lib/src/page/page.dart makes the surface test fail to compile.

The documentation is checked by reading pubspec.yaml for the exact issue_tracker value, reading the library doc comment for the three names and the word experimental, running the analyzer with fatal infos, and reading example/README.md for the checkout requirement and for the absence of any pub.dev availability claim for the companion packages. The root README is checked byte-identical to commit bf6d4795e0f339043487c4f007f1365573adf762.
