# Acceptance criteria: Flutter WebMCP package skeleton

## Frozen

- Frozen at: not yet
- Frozen by: planner (freezes when the implement phase starts)

## Criteria

Every negative case below is a transient mutation applied to a working tree on which the criterion's check already passes. Apply one at a time, observe the stated failure, then revert so that the working tree reports no modifications before the next mutation is applied.

|---|---|---|---|

Re-run: only five stage lines print and the fixed order asserted by the criterion is absent, so the check fails. Restore the script. |
| AC-002 | When the shell's executable search path is set to a fixed minimal value containing neither the `flutter` nor the `dart` binary (for example `/usr/bin:/bin`, which on this machine's toolchain layout resolves neither name but does resolve `python3`), `tools/check.sh` shall exit non-zero with a message naming the missing binary, before any stage line is printed. | Invoke the script once normally (preflight line prints, stages run), then invoke it with `PATH` replaced by the fixed minimal value and read the message and exit status. | Remove the preflight block from the script and invoke it with the replaced `PATH`. Either way the named preflight message never appears before a stage line, so the check fails. Restore the script. |

## Explicitly not required

- Any call to the browser's WebMCP API, including registration, discovery, execution, the change event and abort-signal unregistration. The web transport only detects and logs in this work item.
- Behaviour in a real browser. No criterion here is checked by running the example in Chrome; the example is only required to build and to register its tools in a virtual-machine test, and the web transport's source text is checked without executing it (AC-021).
- Navigation-tool generation from a router. Only the tool-source interface exists; no adapter for any router is required.
- A dev-time or non-browser transport implementation. Only the transport interface and the two skeleton implementations are required.
- Publishing to pub.dev, a pana score, or any comparison against the competing packages.
- A `repository` or `homepage` field in `pubspec.yaml`. Omitted deliberately in this work item; see the plan's Interfaces and Out-of-scope sections.
- A widget wrapper for lifecycle-tied registration, per-screen tool shadowing, typed input decoding, and output schemas.
- Support for any platform other than web, and any lock file being committed.
- Concurrency, isolate safety, or thread safety of the registry beyond single-threaded Dart semantics.
